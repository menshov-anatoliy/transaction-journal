# Design

## Context

Экран «Входящие» (`src/TransactionJournal/Components/Pages/Inbox.razor`) читает все непривязанные сделки одним вызовом `InboxReadModel.ListAsync()` и рисует их без возможности отсечь лишнее. Принцип capability `ui/screens`: UI — тонкий слой над контрактами домена, собственных доменных правил не вводит. Стили экрана живут в `wwwroot/app.css` (классы `toolbar`, `action-form`, `action-label`, `action-input`, `note`, `select-all`). Мотивация — в proposal.md.

## Goals / Non-Goals

**Goals:**

- Блок фильтров «Входящих»: диапазон дат, инструмент (чекбоксы), направление (чекбоксы), действующие одновременно.
- Состояние по умолчанию: последний месяц (скользящее окно от (сегодня − 1 месяц) до сегодня), все инструменты, оба направления.
- «Выбрать всё» и команды разбора корректно работают с видимыми строками при активных фильтрах.

**Non-Goals:**

- Не меняем контракт `InboxReadModel`, доменные сервисы и схему базы: фильтры — представление, а не правило домена.
- Не фильтруем бейдж вкладки и панель каркаса: они считают все непривязанные сделки.
- Не вводим сохранение фильтров между сессиями: это circuit-состояние, как и выбор строк.

## Decisions

### D1. Фильтрация в компоненте, а не в read-модели

Полный список `ListAsync()` остаётся единственным чтением; фильтрация выполняется в `@code`-блоке `Inbox.razor` при отрисовке. Альтернатива — параметры фильтров в `InboxReadModel.ListAsync(...)` — отклонена: список инструментов фильтра строится из всех непривязанных сделок (значит, читать надо всё), а состояние фильтров — circuit-состояние представления, которому не место в контракте read-модели. Объём «Входящих» (материализованные сделки одной биржи) не требует SQL-фильтрации.

### D2. Диапазон дат — поля даты с включительными границами и открытыми концами

Поля «с» и «по» — ввод даты (`input type="date"`). Граница «с» — начало суток указанной даты, «по» — конец суток; сделка проходит, если `ExecutedAt` попадает в интервал включительно. «Последний месяц» по умолчанию считается от текущих суток сервера: «с» = сегодня − 1 месяц, «по» = сегодня. Очищенное поле снимает ограничение с соответствующей стороны (открытый диапазок) — чтобы пользователю не приходилось придумывать дату «от начала времён». Время суток сделки не требует отдельного ввода: дневная гранулярность закрывает задачу поиска сделок.

### D3. Направление — два независимых чекбокса по знаку количества

«Покупка» соответствует `Quantity > 0`, «Продажа» — `Quantity < 0` (нулевого количества в материализованных сделках нет). Снятие обоих флажков даёт пустой видимый список с явным сообщением — без скрытой логики «пусто значит все»: состояние флажков видно на экране и ложно интерпретировано быть не может.

### D4. Инструменты — множество выбранных символов, пересобираемое при каждом чтении

Список инструментов фильтра — упорядоченные уникальные `Symbol` текущего списка «Входящих». После каждого перечитывания (`RefreshAsync`) множество выбранных пополняется новыми инструментами (по умолчанию выбраны все), а исчезнувшие символы из выбора уходят. Так инвариант «по умолчанию выбраны все» держится и после синхронизации, принёсшей новые инструменты.

### D5. Выбор строк ограничен видимыми строками

«Выбрать всё» добавляет execId только видимых (отфильтрованных) сделок; `AllSelected` сравнивает число выбранных с числом видимых. Сделка, скрытая изменением фильтра, исключается из выбора. Иначе массовая привязка молча забрала бы в конструкцию строки, которых пользователь на экране не видит.

### D6. Различимые пустые состояния

Сообщения различаются: «Входящие пусты: непривязанных сделок нет» — когда список пуст целиком, и отдельное сообщение «по заданным фильтрам ничего не найдено» — когда фильтры скрыли все строки. Пользователь видит причину пустого экрана, а не гадает, куда пропали сделки.

### D7. Оформление — существующие классы app.css

Блок фильтров оформляется классами `action-form` / `action-label` / `action-input` и `select-all` поверх текущей темы; при необходимости добавляется минимальный набор классов в `app.css`. Отдельный razor.css-файл для страницы не заводится — экран уже оформлен глобальной темой.

## Risks / Trade-offs

- [Полный список читается при каждом открытии экрана даже при узких фильтрах] → Приемлемо: объём «Входящих» ограничен числом непривязанных сделок; фильтрация в памяти дешевле усложнения контракта read-модели.
- [Часовой пояс сервера определяет «сегодня» для границ по умолчанию] → Журнал — однопользовательский локальный инструмент Blazor Server; часы сервера совпадают с часами пользователя. Если позже появится удалённый доступ, гранулярность «день» переживёт смену пояса безболезненно.
- [Скрытие строк фильтром сбрасывает их выбор] → Плата за предсказуемость массовой привязки (D5); сброс выбора — не потеря данных, строки остаются во «Входящих».

## Migration Plan

Изменение одного экрана без схемы данных и контрактов: выкатывается одним релизом, откат — возвратом предыдущей версии компонента. Специальных шагов миграции нет.
