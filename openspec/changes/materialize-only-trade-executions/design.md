# Design

## Context

Все доменные представления журнала строятся из сырых записей через `TradeMaterializer.Materialize`: «Входящие» (`InboxReadModel`), таймлайны позиций (`PositionReadModel`), метрики (`JournalMetricsReadModel`), сделки конструкции (`ConstructionDetailReadModel`), а остатки для закрывающих записей экспираций `ExpiryMaterializer` считает тем же вызовом материализатора сделок. Сырая строка `RawExecution` хранит `Category` и биржевой `PayloadJson` целиком; тип исполнения (`execType`) доступен только после разбора payload в `BybitExecution.ExecType`. Разброс значений по живой базе: `Trade` (1133 записи в диапазоне выгрузки) и `Funding` (700 записей linear-категории); типы прочих значений биржи (AdlTrade, Settle, Delivery, Liquidation) в базе не встречались. Диагностический сопоставитель сверки уже ограничивает TRADE-вселенную записями `execType=Trade` (change `reconcile-bybit-statement`, решение D9).

## Goals / Non-Goals

**Goals:**

- Одна точка фильтра, через которую проходят все потребители проекции — правка только в `TradeMaterializer`.
- Детерминированное поведение для любого значения `execType`, включая пустое и неизвестное: только `Trade` — сделка.
- Сохранение идемпотентности и переразбираемости: сырье не трогается, повторные материализации дают тот же результат.

**Non-Goals:**

- Доменное представление фандинга (запись начисления, статья PnL, экран) — журнал остаётся журналом сделок.
- Фильтрация при загрузке синхронизацией или в SQL-запросах читателей — хранение сырых записей целиком не меняется.
- Правки валидации привязки `TradeBindingService` — из UI привязать не-Trade запись невозможно, поскольку во «Входящих» её нет.

## Decisions

### D1. Фильтр по `execType` внутри `TradeMaterializer`, до построения сделки
`Materialize` разбирает payload записи, сравнивает `ExecType` с `Trade` и не-Trade запись пропускает: сделка не строится, в результат она не попадает ни сделкой, ни неразрешённым символом. Проверка ставится после разбора payload (тип есть только в нём) и до проверок стороны, цены и количества — фиктивные сделки фандинга не должны требовать «торговых» атрибутов, чтобы быть отброшенными. Альтернативы отклонены: фильтр в каждом read-модели — пять копий одного правила и расхождение при добавлении шестого потребителя; фильтр при записи синхронизацией — нарушает требование «Необработанные записи хранятся целиком».

### D2. Сравнение типа — без учёта регистра, всё прочее — не сделка
Считается `Trade` только значение, равное `Trade` без учёта регистра — та же конвенция, что у сопоставителя диагностической сверки (`StatementMatcher`). Любое другое значение — `Funding`, `AdlTrade`, `Settle`, `Delivery`, пустое, неизвестное будущее значение биржи — трактуется как не сделка по умолчанию: журнал не пытается угадывать смысл незнакомых типов. Альтернатива — явный перечень известных не-Trade типов — отклонена: незнакомый тип попал бы в сделки, а это ровно дефект из issue #17.

### D3. Тихий пропуск без счётчиков и предупреждений результата
`TradeMaterializationResult` не дополняется счётчиком пропущенных записей и предупреждениями: фандинг — регулярное событие линейной торговли (700 за девять месяцев живой базы), предупреждение на каждый синк стало бы шумом, а потребителя счётчика в продукте нет. Видимость не-Trade записей обеспечивают существующие механизмы: сырьё доступно переразбору, диагностическая сверка показывает записи вне TRADE-вселенной по типам. Альтернатива — предупреждение «неизвестный тип исполнения» — отклонена по той же причине шума; новое неизвестное значение биржи проявится в сверке как непарные TRADE-строки выгрузки.

### D4. Применение к живой базе — штатным переразбором, без миграций
Правило разбора применяется существующей командой «Переразобрать» экрана «Настройки» и при чтениях проекцией: 700 фандинг-записей живой базы исчезнут из «Входящих» и перестанут учитываться позициями и метриками без сетевых запросов и изменений схемы. Строка пользовательских данных не-Trade записи (если фандинг был привязан ранее) становится инертной: сделки с таким `execId` нет ни в одном представлении, ни одна проекция её не показывает. Альтернативы — миграция с удалением записей или чисткой userdata — отклонены: сырье правомерно и нужно для переразбора и сверки.

### D5. Калибровка тестовых фикстур: явный `execType: "Trade"` в payload-хелперах
Payload-хелперы тестов `Materialization` и доменных read-моделей не задают `execType`, поэтому под новым правилом их записи перестанут материализоваться — существующие тесты упадут заметно, а не «тихо позеленеют». Хелперы получают `execType: "Trade"` значением по умолчанию; новые тесты фильтра задают `Funding`, прочий не-Trade тип и пустое значение явно. Альтернатива — трактовать пустой `execType` как Trade ради тестов — отклонена: она ослабляет контракт D2 ради удобства фикстур.

## Risks / Trade-offs

- [Биржа введёт новый тип исполнения, который на самом деле является сделкой] → записи типа сохранятся в сырье, переразбор применит новое правило без потери данных, а диагностическая сверка покажет TRADE-строки выгрузки «отсутствует в журнале» — расхождение станет видимым, а не тихим.
- [Тихий пропуск осложняет диагностику «пропавшей» сделки] → правило одно и локализовано в `TradeMaterializer`; сырье и сверка дают полную картину, а в задачах предусмотрен тест, фиксирующий пропуск для каждого класса типов.
- [Фикстуры с пустым `execType` дают ложные падения вне `Materialization`] → падение «сделок не материализовано» однозначно указывает на фикстуру; правка хелперов входит в задачи и не требует правок ассертов.

## Migration Plan

Код реверсится обычным откатом коммита; данные не изменяются ни в прямую, ни в обратную сторону — согласованность проекции с правилом разбора восстанавливается переразбором сырых записей.

## Open Questions

- Нет: поведение для всех значений `execType` определено правилом D2, оставшиеся выборы локальны для `TradeMaterializer`.
