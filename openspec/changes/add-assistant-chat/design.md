# Design

## Context

Архитектура чата консультаций утверждена [ADR-0009](../../../docs/adr/0009-consultation-chat-architecture.md), доменная модель — [CONTEXT.md](../../../CONTEXT.md) и тикетом [#47](https://github.com/menshov-anatoliy/transaction-journal/issues/47); техническая база MEAI/Blazor-стриминга исследована в [#46](https://github.com/menshov-anatoliy/transaction-journal/issues/46). Мотивация — в proposal.md (Why). Этот документ раскладывает решение на проектные шаги без пересказа ADR: размещение, конвейер сообщения, инструменты, персистентность, UI.

## Goals / Non-Goals

**Goals:**

- Новый проект окружения `src/TransactionJournal.Consultations`: порты в проекте, зависимость только от Domain, адаптеры в Infrastructure и composition root.
- Конвейер сообщения: детерминированный снимок контекста → агентный цикл MEAI с тремя read-only инструментами → стриминг ответа с рыночным следом → фиксация сообщения.
- Персистентность per construction в SQLite по образцу `HintStore`; панель «Консультации» в деталях конструкции.

**Non-Goals:**

- Структурированная сущность «План управления» с машинными порогами, портфельные консультации вне конструкции, метрики полезности — v2 (туман карты [#45](https://github.com/menshov-anatoliy/transaction-journal/issues/45)).
- MCP-транспорт инструментов (задел R3 сохраняется), компакция истории, автоторговля, Telegram-канал консультаций.

## Decisions

### D1. Размещение и порты — отдельный проект окружения по ADR-0009

`TransactionJournal.Consultations` повторяет образец Hints (ADR-0007/0008): домен не знает о чате. Порты объявлены в самом проекте: `IConsultationContextReader` (адаптер в Infrastructure поверх read-моделей ConstructionDetail/JournalMetrics), `IRuleCorpusReader` (адаптер в composition root поверх `RulesCorpusLoader` из Hints — без ссылки между проектами окружений), `IConsultationStore` (адаптер SQLite в Infrastructure по образцу `HintStore`). Отклонено: чат внутри Hints (агенты разной природы), внутри Application (тянет ME.AI в оркестрацию).

### D2. Конвейер сообщения — снимок → агентный цикл → стриминг → фиксация

На каждое сообщение: `ConsultationContextReader` собирает markdown-снимок с as-of (конструкция, портфельные агрегаты, индекс корпуса) — код, без LLM; индекс карточек генерируется `IRuleCorpusReader` (id + краткое содержание из 54 карточек). Агентный цикл — keyed `IChatClient` с `UseFunctionInvocation` и `MaximumIterationsPerRequest = 6`; инструкции — `consultation-prompt.md` по паттерну ADR-0007 (настраиваемый путь, дефолт рядом с `rules/`, встроенный дефолт в коде, битость не ломает чат). Ответ стримится `IAsyncEnumerable<ChatResponseUpdate>`; текстовые чанки идут в UI, tool-вызовы накапливаются в рыночный след. По завершении сообщение ассистента фиксируется в `IConsultationStore` с as-of и следом. Отклонено: рынок в базовом промпте — только тулами в момент сообщения.

### D3. Инструменты — три read-only тула через один Bybit-клиент

`read_rule_card(cardId)`, `get_market_snapshot(baseCoin)`, `get_option_board(baseCoin)`. Рыночные тулы ходят исключительно через расширяемый `BybitTickersClient`: DTO `BybitTicker` дополняется опциональными полями (греки/IV/OI/бид-аск/фандинг) тем же эндпоинтом `/v5/market/tickers` — существующие потребители не меняют поведения. Один вызов тула = один HTTP-запрос; троттлер и resilience клиента наследуются, отдельных счётчиков нет; потолок итераций ограничивает биржевые запросы (~6 на сообщение). Доска отдаётся компактной проекцией, а не сырьём. Отклонены: отдельный `BybitOptionBoardClient` (второй троттлер), пер-запросный счётчик и pre-flight ping (структурных мер достаточно).

### D4. Деградация — кэш марок с явным as-of

При ошибке Bybit тул возвращает структурированный ответ «недоступно + последняя кэшированная проекция с as-of» из кэша `InstrumentMarkProvider`; инструкции агента обязывают модель помечать устаревший as-of и отказываться от рыночно-зависимых рекомендаций, отвечая по журналу и корпусу. Чат не падает и не блокируется.

### D5. Персистентность — SQLite per construction, домен не знает

`ConsultationStore` в Infrastructure по образцу `HintStore`: база на конструкцию, таблицы диалогов и сообщений; сообщение — роль, текст, as-of, у ассистента рыночный след (инструменты + as-of). Диалог создаётся первым сообщением, удаляется целиком по команде владельца; компакции нет; пересбор конструкции стирает её консультации вместе со старой записью.

### D6. UI — панель в деталях конструкции, стриминг с троттлингом

Панель «Консультации» на экране деталей конструкции: список диалогов, ввод, стриминг ответа. Перерисовки троттлятся ~150 мс через `InvokeAsync(StateHasChanged)` поверх SignalR-канала; отмена — кнопка с `CancellationToken`; между текстовыми сегментами — статусные строки tool-вызовов, tool-call фрагменты не рендерятся. Закрытая конструкция — тот же конвейер с пост-мортем-промптом из инструкций.

## Risks / Trade-offs

- [Долгий диалог раздувает контекст и бюджет] → Компакции нет by design: владелец начинает новый диалог с чистого листа; снимок компактен.
- [GLM-5.3 дороже Flash] → Бюджет <$5/мес держится короткими диалогами и компактным снимком; при превышении — переход на Air/Flash конфигурацией без кода.
- [Стриминг перегружает SignalR] → Троттлинг перерисовок ~150 мс; отмена через CancellationToken.
- [Расширение DTO BybitTicker заденет существующих потребителей] → Только опциональные поля; поведение провайдера марок и PnL не меняется (покрыто тестами).
- [Модель игнорирует принципы «если/то»/цитирования] → Контракт-тесты проверяют снимок и инструкции; живая приёмка владельцем (LLM-вывод фикстурно не тестируется).

## Migration Plan

Реализация после `add-summary-channels` (реуз настроек провайдера). Порядок: проект и порты → снимок контекста → инструменты и агентный цикл → персистентность → панель UI. Откат — панель не регистрируется в composition root; остальные подсистемы изолированы в проекте окружения, журнал не затронут. Данных для миграции нет: консультации — новая запись окружения.
