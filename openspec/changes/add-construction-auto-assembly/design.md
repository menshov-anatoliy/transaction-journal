# Design

## Context

Журнал хранит сырые исполнения (`RawExecutions`, 1763 linear + 84 option) и deliveries (`RawDeliveries`); домен (конструкции, привязки в `TradeUserdata`, корректировки, комментарии) — производный и пересобираемый. Сейчас конструкции создаются только вручную. Правила сборки, проверенные на полной истории (см. explore-протокол и Python-эталон в материалах сессии), дают 10 конструкций и 974 из 975 торговых сделок в привязках (873 linear-Trade + опционные; 1 linear-сделка во «Входящих»). Контрольные числа учитывают доменное правило «фандинг — не сделка» (`openspec:sync/bybit-history#requirement-non-trade-executions-are-not-trades`): черновые числа эталона 1761/2 считали все 1763 linear-записи вместе с 872 фандинговыми и в тест-сверке не используются. Мотивация — в proposal.md, контракт поведения — в дельтах specs.

## Goals / Non-Goals

**Goals:**

- Use-case «пересобрать конструкции»: полный пересбор с нуля одним действием, детерминированный и идемпотентный.
- Точная реализация правил v5: окно 60 минут, погашение у владельца, переживший/ранний владелец, усреднение с проверкой страйк+доска, запрет усреднения в день экспирации, закрытие по нулевым ногам с учётом deliveries.
- Кнопка на «Настройках» с подтверждением и итогом-счётчиками.

**Non-Goals:**

- Автозапуск сборки в конце синхронизации (решение пользователя — только явная кнопка).
- Изменение схемы БД и миграции: таблицы существуют, пересборка работает с данными.
- Правка правил домена позиций/FIFO, аналитики и синхронизации.
- Автоматическая коррекция «компромиссных» группировок (лотто 25JAN, скальп SOL, шорт пута) — правится вручную после сборки.

## Decisions

- **D1. Сборка — use-case сервис домена, читающий сырье напрямую.** `ConstructionAssemblyService` (Domain) принимает снимок сырых записей (`IJournalRawSnapshotStore` + deliveries), вычисляет группы в памяти, затем в одной транзакции вычищает `Constructions`, `TradeUserdata`, `PnLAdjustments`, `PositionComments`, `ManualCloseMarks` и наполняет заново. Альтернатива — встраивание в конец синхронизации или в `JournalReparseService`: отклонено, чтобы пересборка оставалась явным действием и не мешала сверке репарсера. Удаление — прямым вычищением таблиц, а не поштучным `ConstructionService.DeleteAsync`: последнее запрещает непустые конструкции по требованию домена, пересборка — карв-аут.
- **D2. Алгоритм — детерминированный проход окон v5.** Порядок записей: (`ExecTimeMs`, `ExecId`). Окно: подряд идущие исполнения одного базового актива с зазором ≤ 60 минут; delivery-запись окно обрывает и гасится у владельца ноги немедленно. Ролл: закрывающий трейд (продажа при held > 0, откуп при held < 0) погашается у владельца-конструкции (первый по `(opened_at, id)`); цель присоединения открывающих: пережившая окно (ненулевой остаток после погашений), иначе ранняя среди владельцев. Усреднение: без владельцев, единственная живая конструкция актива, день окна не равен дню экспирации её максимальной доски, и (одноногое окно либо каждая нога повторяет пару «страйк+доска» имеющейся ноги); иначе новая конструкция. Закрытие: все ноги нулевые (не сумма). Полная спецификация — в дельте `domain/construction-assembly`; арифметика на `decimal`. Эталон-проверка — Python-прототип из explore.
- **D3. Привязка робота по активу и периоду.** Базовый актив linear-символа = отбрасывание суффикса `USDT` (`ETHUSDT` → `ETH`); сопоставление с опционными активами точное. Период жизни: `[первое исполнение конструкции .. время закрытия]`, у живых — открытый конец. Перекрытие: конструкция с меньшим `(opened_at, id)`. Альтернатива (разбиение робота на отдельные конструкции по паузам) отклонена пользователем.
- **D4. Имена конструкций — из открывающего окна.** «{Актив} {стреддл|стренгл|колл-спред|пут-спред|CALL|PUT} {доска} {страйк(и)}» (примеры: «ETH стреддл 25SEP26 1600», «BTC колл-спред 25DEC26 85000/120000»). Имя чисто презентационное: переименование свободно и на детерминизм не влияет.
- **D5. Контракт пересбора.** Результат — счётчики: конструкций создано, сделок привязано, сделок во «Входящих» (число `RawExecutions` без строки в `TradeUserdata` с ненулевой привязкой). UI «Настроек» вызывает сервис напрямую (как репарсер), показывает подтверждение с перечнем потерь и итог.
- **D6. Тесты.** Юнит-тесты правил на синтетических наборах (каждый сценарий дельты — тест); интеграционный тест на репрезентативной выгрузке истории со сверкой контрольных показателей (10 конструкций, 974 привязки торговых сделок, 1 во «Входящих», закрытие deliveries) — фиксация ожиданий в тестовой фикстуре снимка сырья, без обращения к живой БД.

## Risks / Trade-offs

- [Эвристики окна/усреднения могут неверно сгруппировать будущие сделки] → правила задокументированы в спеке, ручной перенос сделок остаётся, пересборка повторяема после правки алгоритма.
- [Безвозвратная потеря ручных данных по кнопке] → обязательное подтверждение с перечнем потерь; рекомендация резервной копии базы в тексте подтверждения.
- [Параллельный запуск пересборки и синхронизации] → пересборка читает снимок сырья и выполняется короткой транзакцией; синхронизация дописывает сырье, конфликт ограничен повторным запуском пересборки.
- [Расхождение C#-реализации с Python-эталоном] → интеграционный тест со сходимостью на контрольных показателях истории.

## Migration Plan

Схема БД не меняется — миграций нет. Ввод в действие: деплой, нажатие «Собрать конструкции» на новой базе после полной синхронизации. Откат: пересборка после правки алгоритма либо восстановление базы из резервной копии.

## Open Questions

Нет: все развилки (окно 60 мин, перекрытие — ранняя конструкция, стирание ручных данных, кнопка) зафиксированы пользователем в explore.
