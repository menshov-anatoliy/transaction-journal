# Design

## Context

Журнал считает метрики при чтении: «Аналитика вычисляется при чтении и не хранится» (`openspec:analytics/performance#requirement-analytics-computed-on-read`), сборка детерминирована, ручные данные живут отдельными таблицами SQLite (`ManualCloseMarks`, `PnLAdjustments`, `TradeUserdata`) и переживают инкрементную сборку, но стираются пересбором. Символы опционов уже разбираются на базу/экспирацию/страйк/тип (расчёт реального риска). Мотивация и границы — `proposal.md` и ADR-0014; логический слой не меняет инструментальную истину.

## Goals / Non-Goals

**Goals:**

- Детерминированное распознавание синтетических связок как чистой функции записей конструкции.
- Паритетный лок «зафиксировано синтетикой» к экспирации, независимый от марок.
- Ручное оспаривание связок с жизненным циклом ручных данных.

**Non-Goals:**

- Неттинг синтетики в инструментальные позиции, остатки и «Реализованный результат».
- Изменение реального риска, нереализованного PnL, индикатора финрезультата, статуса закрытия (ADR-0006).
- Подсказки на основе распознавания (триггер `synthetic-close-itm` уже существует и не меняется).

## Decisions

### 1. Распознавание вычисляется при чтении, а не хранится в сборке

Распознаватель — чистая функция над записями конструкции в Domain (`ConstructionAssembly` рядом с классификацией окон), вызываемая read-model'ю деталей. Альтернатива — фиксировать связки в сборке: отвергнута, дублирует истину, требует инвалидации при ручной перепривязке сделок и противоречит философии «аналитика не хранится». Детерминизм следует из чистоты функции (`scenario-recognition-recomputation-stable`).

### 2. Шаблон сопоставления

Для каждой конструкции записи упорядочиваются по времени и execId. Линейное исполнение образует связку с встречным опционным исполнением, когда: та же база; окно ≤ 60 минут (та же константа окна, что в сборке); встречный опцион — противоположного типа к открытой опционной ноге той же доски (страйк и экспирация совпадают); количества равны; направления по `ac-43` (закрытие длинного PUT — Buy фьючерс + Sell CALL; длинного CALL — Sell фьючерс + Sell PUT). Каждое исполнение входит не более чем в одну связку; при нескольких кандидатах берётся раннее по времени, затем по execId. Единицы количества опциона и линейного фьючерса XAUT совпадают (1 контракт = 1 XAUT) — проверено на реальных данных 15.10.2026.

### 3. Записи оспаривания — новая таблица ручных данных

`SyntheticCloseDisputes` (EF-миграция): ключ — `ConstructionId` + пара `ExecId` линейной и встречной опционной сделок (execId стабилен, уже служит ключом `TradeUserdata`). Инкрементная сборка таблицу не трогает; пересбор стирает вместе с прочим содержимым конструкций (дельта `domain/construction-assembly`). Альтернатива — флаг на сделке: отвергнута, спор принадлежит связке из двух сделок, а не одной.

### 4. Формула лока

На связку: `qty × |страйк − цена линейной сделки| + премия встречного опциона − FIFO-стоимость входа закрываемой части ноги − (комиссии линейной и опционной сделок + FIFO-доля комиссий входа ноги)`. FIFO-доли переиспользуют примитивы расчёта комиссий и средних из `analytics/performance`, паритет USDC→USDT по ADR-0001. Величина не читает марки — деградация котировок её не касается.

### 5. Контракт API и UI — аддитивные поля

Read-model деталей и HTTP-ответ получают поля `syntheticCloses[]` (связка: нога, количество, величина лока) и `disputed`-признак; транспортные требования `http-api/transport` не меняются, обновляется только OpenAPI-описание. В UI строка «зафиксировано синтетикой» добавляется в сводку деталей, позиция линейной ноги показывает распад «синтетика / прочий остаток»; визуальный источник истины — design.pen (ADR-0011), принимается скриншот-сверкой.

## Risks / Trade-offs

- [Ложные срабатывания: хедж-сделка совпала с опционной по доске и количеству] → точное равенство количеств, окно и порядок кандидатов детерминированы; штатный выход — оспаривание связки.
- [Спор стирается пересбором] → принятое следствие семантики пересбора, единое с ручными пометками закрытия; предупреждение в UI не требуется (консистентно с существующим поведением).
- [Расхождение единиц контрактов на других базах в будущем] → распознаватель требует равенства единиц; при появлении базы с иным размером контракта — отдельная правка формулы сопоставления.

## Migration Plan

Аддитивная EF-миграция (новая таблица споров), без бэкфилла: на живой базе связки распознаются сразу при чтении. Откат — удаление таблицы; инструментальные данные не затрагиваются ни на одном шаге.
