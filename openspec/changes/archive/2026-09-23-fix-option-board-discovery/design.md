# Design

## Context

См. proposal.md — Why. Текущее состояние: `OptionBaseCoinSource` перечисляет доску одним безфильтровым запросом `instruments-info?category=option` и получает только доску по умолчанию (BTC); `ExecutionCategorySync` строит по этому перечню области перебора и при пограничном исчерпании прерывает весь перебор категории; предупреждения запуска живут только в состоянии компонента страницы синхронизации. Живыми запросами 2026-09-23 установлено: `instruments-info` и `tickers` без `baseCoin` не перечисляют доску целиком (tickers для option вообще отказывает без `baseCoin`), `execution/list` без фильтра возвращает записи всех активов аккаунта, `delivery-price` начинает перечисление с доски по умолчанию и непригоден как источник перечня.

## Goals / Non-Goals

**Goals:**

- Гарантированная полнота выгрузки исполнений option по всем активам аккаунта без ручной конфигурации каждого нового актива.
- Самозаживление покрытия: актив, впервые встреченный безфильтровым проходом, получает отдельную область со следующего запуска.
- Пограничное исчерпание и пропуск области действуют в границах одной области, не отменяя обход остальных.
- Предупреждения запуска переживают перезагрузку страницы.

**Non-Goals:**

- Автоматическое исправление уже зафиксированного водяного знака: история ниже водяного знака восстанавливается существующей командой сброса состояния категории, автоматических повторных переборов не появляется.
- Перечисление всех досок биржи вообще (в т.ч. активов, по которым у аккаунта нет истории) — вне досягаемости API и не нужно журналу.
- Изменение справочника спецификаций и материализации: контракт `requirement-instrument-reference` не меняется.

## Decisions

### D1. Области option: безфильтровый проход плюс по-активные области из объединения источников

`ResolvePassScopesAsync` для option возвращает `null`-область (проход без фильтра — первыми по порядку) плюс по-активные области. Перечень активов — объединение: живое перечисление `instruments-info` (даёт доску по умолчанию), активы записей сырьевого хранилища (distinct-префиксы до первого дефиса символов option-исполнений и delivery-записей), конфигурация `Sync:ExtraOptionBaseCoins`. Активы нормализуются как сейчас (trim, верхний регистр), порядок стабилен.

Безфильтровый проход — одновременно загрузка и обнаружение: он закрывает интервалы, которые по-активные области ещё не покрывают (новый актив до попадания в перечень), и его записи пополняют сырьевое хранилище — источник перечня следующего запуска. По-активные области остаются исчерпывающим механизмом: параметр `baseCoin` документирован, полнота по активу не зависит от недокументированного поведения безфильтрового ответа. Дубли между проходами снимаются существующей идемпотентностью по `execId`.

`null`-область не считается покрытием актива в `PassedBaseCoins` — семантика детектора непокрытых активов из change `add-delisted-instrument-resilience` сохраняется: актив, чьи записи приняты безфильтровым проходом, но чья область не проходилась, подсвечивается один запуск и закрывается следующим.

Альтернативы: положиться только на безфильтровый проход (отвергнуто: полнота безфильтрового ответа не задокументирована биржей и уже опровергалась ранее для других эндпоинтов); положиться только на конфигурацию (отвергнуто: ручное сопровождение, дыра при каждом новом активе — исходный дефект).

### D2. Источник активов сырья: отдельный read-запрос над хранилищем

`OptionBaseCoinSource` получает вторую зависимость — читатель distinct-символов option-записей сырьевого хранилища (исполнения и delivery). Реализация — метод над `JournalSyncStore`: выборка distinct `Symbol` обеих таблиц категории option с разбором префикса в памяти; объём (сотни символов) не требует SQL-разбора строки. Читатель вызывается в начале запуска при построении перечня областей.

Альтернатива: полная загрузка снимка сырья для извлечения активов — отвергнута: снимок читается целиком позже в оркестраторе, двойная загрузка не оправдана ради перечня.

### D3. Пограничное исчерпание — в границах области

Флаг `boundaryExhausted` перестаёт прерывать foreach по областям: повторный пограничный отказ завершает while-цикл текущей области, перебор продолжается со следующей области. Для категорий с единственной областью (linear, delivery, а также сам безфильтровый проход option) поведение не меняется. `HistoryExhausted` в инкрементальном режиме означает «хотя бы одна область исчерпана погранично» — флаг остаётся отчётным, состояние категории не зависит от него.

Пропуск области по 110023 уже действует в границах области — не меняется.

### D4. Предупреждения запуска сохраняются колонкой записи запуска

`SyncRuns` получает nullable-колонку `WarningsJson` (EF-миграция): JSON-объект с тремя перечнями — `skippedAreas` (объединение исполнение+delivery по категориям), `unresolvedInstruments`, `uncoveredBaseCoins`. Оркестратор после успешного закрытия запуска и построения проекции сохраняет предупреждения отдельным обновлением записи запуска; сбой сохранения не роняет результат запуска.

Страница синхронизации: `SyncJournalReadModel` отдаёт последний завершённый запуск с разобранными предупреждениями; когда в памяти компонента нет свежего `_result`, страница показывает блок последнего запуска (статус, режим, счётчики — уже хранятся — и предупреждения). После нажатия кнопки блок строится из `_result` как сейчас.

Альтернатива: пересчитывать предупреждения при загрузке страницы из снимка — отвергнута: пройденные области запуска не хранятся, детерминированный пересчёт требует состояния, которого нет.

### D5. Восстановление данных реального журнала — сброс категории option

После выката: команда «Сброс состояния категории option» (существует, с подтверждением) → следующий запуск делает backfill: безфильтровый проход вытянет историю ETH и XAUT всей глубиной (полнота безфильтрового ответа подтверждена живым прогоном), области BTC и ETH (последняя — из delivery-записей снимка) пройдут отдельно; XAUT получит собственную область со следующего запуска. Конфигурация `Sync:ExtraOptionBaseCoins` для ETH/XAUT не требуется.

## Risks / Trade-offs

- [Безфильтровый проход может молча усекаться биржей до актива по умолчанию] → по-активные области остаются гарантом полноты по каждому известному активу; детектор непокрытых активов подсвечивает актив без собственной области; механизмы прикрывают друг друга.
- [Рост числа запросов option-категории примерно вдвое] → лимит эндпоинта 50 req/s и ручной режим запуска; дедуп по `execId` исключает дубли строк; цена признана приемлемой.
- [История ниже уже зафиксированного водяного знака не возвращается сама] → восстановление — существующая команда сброса состояния категории (D5); автоматизация отложена как отдельная работа, если понадобится.
- [Старые записи `SyncRuns` без предупреждений] → колонка NULL, рендер трактует как отсутствие заметок.

## Migration Plan

1. EF-миграция: колонка `SyncRuns.WarningsJson` (TEXT, NULL) — совместима со старыми записями; развёртывание обычное, без остановки.
2. Откат: миграция вниз; код отката читает NULL как отсутствие предупреждений.
3. Эксплуатационный шаг после выката — D5 (сброс категории option и контрольная сверка «Входящих» с биржевым экспортом).
