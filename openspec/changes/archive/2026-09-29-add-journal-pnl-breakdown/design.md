# Design

## Context

Журнал-уровневый итог живёт в `JournalMetrics.TotalPnL`: `JournalMetricsReadModel` суммирует итоги конструкций и гасит итог в null при сбое марок хотя бы одной конструкции. Верхняя панель (`MainLayout.razor`) читает `IJournalMetricsReadModel` напрямую и выводит строку «итог по журналу»; сводка экрана «Конструкции» получает итог через `ConstructionListData` из `ConstructionListReadModel`. Метрики конструкции уже несут `RealizedPnL` (всегда доступен) и `UnrealizedPnL` (null при неоцененном остатке) — журнал-уровневая разбивка не требует новых вычислений, только агрегацию по тем же правилам.

## Goals / Non-Goals

**Goals:**

- Журнал-уровневые агрегаты реализованного и нереализованного PnL в контракте аналитики с деградацией только нереализованной части.
- Вывод разбивки в обоих местах итога: верхняя панель и сводка экрана «Конструкции».

**Non-Goals:**

- Сумма корректировок и проценты от капитала на уровне журнала — пользователь их не запрашивал; тождество «реализованный + нереализованный + корректировки = итог» остаётся на уровне конструкции.
- Изменение правил расчёта PnL, марок или хранения: агрегаты производны и вычисляются при чтении.

## Decisions

### D1. Агрегаты в `JournalMetrics`, не в UI-моделях

`JournalMetrics` получает `RealizedPnL` (`decimal`, всегда доступен) и `UnrealizedPnL` (`decimal?`). `RealizedPnL = Σ ConstructionMetrics.RealizedPnL` по всем конструкциям, включая архивные; `UnrealizedPnL = null`, если хоть одна конструкция без оценки, иначе сумма. Итог не меняется. Альтернатива — считать суммы в UI-моделях — отвергнута: обе точки вывода (панель и сводка) дали бы дублирующую логику агрегации в тонком слое UI, а правила null-деградации — доменное правило аналитики.

### D2. Семантика null повторяет итог, а не изобретает новую

Нереализованный агрегат гаснет при сбое марок любой конструкции — то же правило, что у существующего итога. Частичная сумма с пометкой «неполностью» отвергнута: пользователь принял бы сумму без открытых конструкций за полный результат. Реализованный агрегат не nullable: сбой марок его не затрагивает, и панель сохраняет полезную информацию в любом состоянии.

### D3. Панель — компактная строка, сводка — ячейки

`MainLayout.TotalLabel` расширяется до «итог по журналу: X USDT (реализов. A / нереализов. B)»; при сбое марок — «итог по журналу: неполный (сбой марок), реализов. A, нереализов. —». Сводка `Constructions.razor` добавляет в `kstrip` ячейки «реализованный» и «нереализованный» с теми же правилами знака и признаком сбоя, что у существующих величин. Оба места пользуются одним форматтером величин PnL, чтобы формат «+0.##/-0.##» не разъезжался.

### D4. `ConstructionListData` переносит разбивку как есть

`ConstructionListReadModel` остаётся тонким: добавляет `metrics.RealizedPnL` и `metrics.UnrealizedPnL` в `ConstructionListData` без пересчёта — как сегодня переносит `TotalPnL`, `MarksAsOf` и `HasMarkFailure`.

## Risks / Trade-offs

- [Тождество «реализованный + нереализованный ≠ итог» при наличии корректировок может удивить] → Явные слова в spec-сценарии `scenario-journal-breakdown-excludes-adjustments`; ячейки разбивки в сводке соседствуют с итогом, а не раскрывают его.
- [Строка панели удлиняется, на узких экранах может не влезать] → Компактные подписи «реализов./нереализов.»; при необходимости перенос внутри блока панели, не отдельная строка данных.
- [Рост количества тестов UI-строк панели] → Переиспользовать существующие фикстуры метрик в `AppFrameTests`, добавляя разбивку к уже проверяемым состояниям (полный итог, сбой марок, загрузка).

## Migration Plan

Хранилище и миграции не затрагиваются. Откат — возврат вывода к одному итогу; контрактные поля можно оставить совместимыми, поскольку consumers только читают.
