# Design

## Context

«Марка» — исторический русский термин проекта для mark price Bybit: цены биржевой оценки инструмента из публичного тикера (`markPrice`), лежащей в основе нереализованного PnL, стоимости остатков, процента изменения цены и оценок чат-инструментов. Термин пронизывает все слои: домен, аналитику, read-модели, API, TS-типы, UI-тексты, глоссарий, specs и макет `design.pen` (~1025 кириллических вхождений в 226 файлах, ~366 `Mark*`-идентификаторов в C#). Мотивация — см. proposal.md (Why).

Ограничения: SPA и API поставляются одним exe (ADR-0003), внешних потребителей HTTP-контракта нет; БД — SQLite через EF Core; UI-слой ведётся по ADR-0011 (design.pen — источник истины); живые specs несут стабильные `Traceability ID`.

## Goals / Non-Goals

**Goals**

- Единственная русская словоформа термина во всех слоях: «котировка/котировки/котировку/…»; слово «марка» в проекте не остаётся.
- Согласованное английское именование на корне `Quote`/`QuotePrice` в C# и TS.
- Обновление живых specs дельтами без изменения поведения и без переименования Traceability ID.

**Non-Goals**

- Изменение поведения, расчётов, статусов деградации или сценариев — меняются только имена и тексты.
- Переименование внешних wire-полей Bybit (`markPrice`, `markIv`) в маппингах внешних ответов — это чужой контракт.
- Переименование Traceability ID (включая исторические `…mark…`-корни) и `openspec/changes/archive/**`.
- Слова «маркер» (маркер итога, `Marker*`), «маркировать/маркировка», «Markdown» — это не термин «марка».
- Переписывание исторических файлов миграций.

## Decisions

### D1. Русский термин и механика замены

Канон — «котировка»; замена словоформ механическая и проверяемая:

| Было | Стало |
|---|---|
| марка/марки/марку/марке/маркой/маркам/марках/марками | котировка/котировки/котировку/котировке/котировкой/котировкам/котировках/котировками |
| марок | котировок |
| «по средним маркам» | «по средним котировкам» |
| «сбой марок», «последняя известная марка» | «сбой котировок», «последняя известная котировка» |

Регэксп замены: `[Мм]арк(?!ер|иров)` → `[Кк]отировк`, отдельно `[Мм]арок` → `[Кк]отировок`. Lookahead исключает «маркер» и «маркировать/маркировка». Тот же набор правил применяется в коде-комментариях, UI-текстах, docs и specs; дельты этого change уже сгенерированы им (сверка: 0 остатков).

Альтернатива — «mark-цена»/транслитерация — отклонена: пользователь явно выбрал «котировка».

### D2. Английская основа `Quote`, пометка закрытия — `Annotation`

- `MarkPrice` → `QuotePrice`, `markPrice` → `quotePrice` (внутренние DTO, JSON-контракт, TS-типы).
- `InstrumentMarkProvider` → `InstrumentQuoteProvider`, `UnrealizedPnlMarkEvaluator` → `UnrealizedPnlQuoteEvaluator`, `IMarkSource` → `IQuoteSource`, `HintsMarkSource` → `HintsQuoteSource`, `ManualCloseMark` → `ManualCloseAnnotation`, `ManualCloseMarkService` → `ManualCloseAnnotationService`; остальные члены — по тому же корню (полный список фиксируется задачей-инвентаризацией по grep `\bMark`).
- `ManualCloseMark` — это пользовательская пометка закрытия, а не цена (см. GLOSSARY «Ручная пометка закрытия»), поэтому корень не `Quote`, а `Annotation`.
- Bybit-маппинги (`BybitTicker.MarkPrice` и т.п.) сохраняют имена внешних полей; внутренние проекции переименовываются.

Альтернатива `Quotation` — отклонена как более длинная и не идиоматичная.

### D3. Контракты и БД

- HTTP/JSON: поле `markPrice` → `quotePrice` во всех ответах эндпоинтов; TS-типы и маппинги обновляются в том же блоке работ. **BREAKING** — принят: потребители только собственный SPA.
- SQLite: новая EF-миграция переименовывает колонки `MarkPrice` → `QuotePrice` (EF выполняет rebuild таблицы). Исторические миграции не переписываются — они фиксируют прошлое именование.
- Traceability ID не переименовываются: идентификаторы стабильны по конвенции, ссылки из кода и тестов продолжают разрешаться.

### D4. Design-first (ADR-0011)

Первый шаг UI-блока — правка `design.pen` через MCP Pen: тексты макета («подставлена последняя марка инструмента», «открытый остаток по текущим маркам…», подписи маркера итога) переходят на «котировку». Затем перенос во фронтенд и обязательная скриншот-сверка живой страницы с макетом.

### D5. Specs и параллельный change

- Дельты (`## MODIFIED Requirements`, 25 требований в 8 capabilities) уже записаны в этом change; живые specs обновятся при sync/архивации. Сценарии и Traceability ID внутри требований сохранены.
- Заголовки требований и сценариев внутри дельт остаются исходными («марка»-словами): OpenSpec сверяет MODIFIED-блоки с живым spec по тексту заголовка, и их переименование в дельте ломает archive. Переименование заголовков — прямой sweep живых specs после archive (задача 4.4), вместе с Purpose-абзацами.
- Purpose-абзацы capabilities и тексты вне требований (где replace не применим дельтами) закрываются финальным grep-sweep после sync.
- Активный change `add-summary-channels` ещё не синхронизирован — его дельта `hints/summary-digest` правится точечно («Марки: …» → «Котировки: …», «время рыночных марок» → «время рыночных котировок»).

## Risks / Trade-offs

- [Рассинхрон API и TS-типов] → переименование контракта и типов одним блоком; зелёные билд и тесты как gate.
- [EF-миграция rebuild таблицы в SQLite может потерять данные при ошибке] → миграция проверяется на копии БД; колонка переименовывается без изменения типа.
- [Полуавтоматическая замена может задеть чужие слова] → lookahead-исключения + финальный grep `[Мм]арк(?!ер|иров)|[Мм]арок` по репозиторию (ожидание: 0 вне `archive/**`, `.wf-research`, wire-маппингов Bybit).
- [Исторические идентификаторы с корнем `mark` в Traceability ID остаются] → осознанно: стабильность id важнее косметики; слово «марка» в русском тексте при этом исчезает.
- [Пользовательские сохранённые фильтры/состояния с `markPrice`, если появятся] → внешних потребителей нет; проверяется grep-сводкой перед выпуском.

## Migration Plan

1. Документация решения: GLOSSARY.md и ADR-0019 — уже созданы в сессии планирования.
2. `design.pen` → фронтенд-тексты → скриншот-сверка (UI-блок).
3. Бэкенд: переименование типов/членов/файлов, JSON-контракта, комментариев; новая миграция колонок.
4. Фронтенд: TS-типы, маппинги, тексты.
5. Спеки: точечная правка `add-summary-channels`; живые specs — при sync/архивации change.
6. Откат — обратный коммит; миграция вниз предусмотрена EF (обратное переименование колонок).
