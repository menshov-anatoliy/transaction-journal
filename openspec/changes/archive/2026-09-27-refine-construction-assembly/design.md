# Design

## Context

Алгоритм v5 (`ConstructionAssembler`) строит план из полного снимка сырья: окна 60 минут, роллы, усреднение в единственную живую конструкцию актива. `ConstructionAssemblyService.RebuildAsync` применяется вычищением доменных таблиц; имя фиксируется при открытии окна (`ConstructionNameBuilder.BuildName` по составу ног без размеров); статус при пересборе всегда `Open`. Контрольная сверка `ConstructionAssemblyHistoryReconciliationTests` держит эталонные числа истории. Мотивация и правила — в proposal.md; решения сессии планирования — ADR-0004 (два режима сборки) и ADR-0005 (производный нейминг).

## Goals / Non-Goals

**Goals:**

- Инкрементная сборка только из «Входящих» с чтением существующих конструкций как контекста и записью производных атрибутов (имя, статус).
- Эвристика доски для выбора цели усреднения при нескольких живых конструкциях актива.
- Нейминг v2 по лексике трейдера: акцент, ratio, направление; пересчёт при изменении состава ног; фиксация ручным переименованием.
- Статус «открыта»/«закрыта» следует за опционным прикрытием; «архив» неприкосновенен.
- Один и тот же `ConstructionAssembler` для обоих режимов — пересбор есть частный случай с пустым seeded-состоянием.

**Non-Goals:**

- Слияние режимов: пересбор и инкремент остаются разными командами (ADR-0004).
- Устранение расхождения на разрезанном ролле (принято, ADR-0004).
- Автозапуск сборки после синхронизации.
- Изменение правил привязки фьючерсов робота (период жизни = период прикрытия, без изменений).

## Decisions

### d1. Seeded-состояние assembler вместо второго алгоритма
`ConstructionAssembler.Assemble` получает опциональное начальное состояние: существующие конструкции (стабильный ключ БД, имя, признак ручного имени, статус, `OpenedAtMs`/`ClosedAtMs`, ноги с остатками). Полный пересбор вызывает его с пустым состоянием — поведение сводится к текущему. Альтернатива — отдельный инкрементный алгоритм — отклонена: два кодовых пути разошлись бы в правилах.

### d2. Остатки ног считаются тем же способом, что и позиции чтения
Остаток ноги существующей конструкции = агрегат привязанных сделок (Trade-исполнений по символу) плюс закрывающие записи (delivery/OTM из сырья, ручные пометки). Переиспользуется логика вычисления остатков читающего слоя позиций — без дублирования формулы. Порядок seeded-конструкций: `(OpenedAtMs, Id)` — детерминирован.

### d3. Вход инкремента — «Входящие» плюс полный таймлайн delivery-событий
Окна строятся только из исполнений, отсутствующих в `TradeUserdata` (тот же критерий, что у читающей модели «Входящих»). Delivery-события (сырые + выведенные OTM по `asOf = now`, по ADR-0002) применяются ко всему состоянию: экспирации, наступившие между прогонами, гасят ноги владельцев и закрывают конструкции. Без этого инкремент никогда бы не узнал об исчезновении прикрытия.

### d4. Эвристика доски в выборе цели усреднения
`FindAveragingTarget`: при нескольких живых конструкциях актива одноногое окно ищет живые конструкции с ногой той же доски (датой экспирации), что и нога окна; кандидат обязан быть единственным и пройти прежний запрет дня экспирации. Ноль или больше одного кандидата — новая конструкция. Многоногое окно при нескольких живых не усредняется вовсе (прежнее поведение). Многодневные ноги (стреддл за 48 дней) остаются покрытыми случаем единственной живой конструкции.

### d5. Нейминг v2: вид из живых ног с размерами
`ConstructionNameBuilder.BuildName(baseCoin, legs с количеством)`: «стреддл» (равные размеры), «стреддл с акцентом вверх/вниз N:M» (неравные, направление по доминирующей ноге, N:M — целочисленное сокращение по НОД при целых размерах), «стренгл»/«стренгл с акцентом», «колл-спред N:M»/«пут-спред N:M», «направленная CALL/PUT». Сегменты досок и страйков форматируются как сейчас. Имя пересчитывается из ненулевых опционных ног: при создании, после каждого окна (attach/repay) и после delivery-гашения; при полном обнулении сохраняется последнее производное имя. Альтернатива «имя только при закрытии» отклонена: живая конструкция должна зваться по смыслу уже сейчас.

### d6. Флаг ручного имени в БД
`Construction.NameIsManual` (bool, default false, миграция SQLite). Сервис переименования выставляет `true`; сборка и пересбор не трогают имя конструкций с `true` (пересбор стирает всё — флаг уходит вместе с конструкцией). Ручное имя — единственная точка отключения автогенерации (ADR-0005).

### d7. Статус следует за прикрытием
Внутри прогона вычисляется производный признак «все опционные ноги нулевые» (существующее `ClosedAtMs`-правило). План сборки возвращает статусные переходы: `Open` при ненулевой опционной ноге, `Closed` при полном обнулении ног. Статус `Archived` у существующей конструкции блокирует статусные переходы и смену имени, но не мешает погашению остатков. В БД статус пишется только для конструкций, затронутых прогоном.

### d8. Use-case инкремента и применение плана одной транзакцией
`IConstructionAssemblyService` получает `AssembleInboxAsync`: снимок «Входящих» + seeded-состояние → план → одна транзакция: вставка новых конструкций, вставка `TradeUserdata` для новых привязок (ключ — существующий или freshly-inserted Id конструкции), точечные `UPDATE` имени/статуса затронутых существующих конструкций. Ручные данные не читаются на запись вовсе. Итог — те же счётчики, что у пересбора.

### d9. UI: две команды в «Настройках»
Рядом с «Собрать конструкции» (пересбор, подтверждение сохраняется) добавляется «Собрать из „Входящих"» без подтверждения; обе показывают итог (создано/привязано/осталось) и обновляют список конструкций и бейдж «Входящих».

### d10. Контрольная сверка обновляется под нейминг v2 и доску
Эталонные имена в `ConstructionAssemblyHistoryReconciliationTests` пересчитываются после прогона новой сборки на фикстуре (в т.ч. «стреддл 1600» и цепочка 29MAY); числа конструкций/привязок пересчитываются, если эвристика доски изменила группировку истории. Сверка остаётся критерием приёмки детерминированности.

## Risks / Trade-offs

- [Разрезанный ролл даёт лишнюю конструкцию в инкременте] → принято (ADR-0004); редкий случай, чинится ручной привязкой; документировано в спеке.
- [Эвристика доски может присоединить докупку не туда при двух живых конструкциях одной доски] → при неоднозначности открывается новая конструкция (перестраховка); ручная привязка доступна.
- [Имя меняется под пользователем] → только для незафиксированных имён; `NameIsManual` — явная точка контроля; смена имени не влияет на группировку и расчёты.
- [Рост объёма прогона со временем — seeded-состояние растёт] → остатки считаются одним агрегатом по БД; полный пересбор остаётся средством «сброса» состояния при желании.

## Migration Plan

1. EF-миграция: `Construction.NameIsManual` (bool NOT NULL default 0).
2. Код и тесты разворачиваются одной сборкой; инкрементная команда появляется в UI сразу, пересбор меняет только нейминг/статусы.
3. Откат: возврат коммита; колонка безвредна для старого кода (не читается).

## Open Questions

Нет — контрольные числа истории уточняются при выполнении задачи d10 по факту прогона на фикстуре.
