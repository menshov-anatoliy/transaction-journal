# Design

## Context

Сортировка позиций и сделок выполняется при чтении в presentation read-моделях: `ConstructionDetailReadModel` упорядочивает позиции (`ReadPositionsAsync`: открытые → CALL → PUT → прочие → тикер → экспирация по возрастанию) и сделки (`ReadTradesAsync`: по возрастанию времени исполнения); `InboxReadModel` возвращает сделки в хронологическом порядке материализатора. Разбор символа опциона уже есть — `OptionSymbolParser.TryParse` отдаёт `ExpiryDate`, `Strike` и `Type`, но страйк в текущую сортировку не входит. Хронологический порядок вывода `TradeMaterializer.Materialize` — детерминизм доменных движков (FIFO, экспирации), его потребители: `ExpiryMaterializer`, `PositionReadModel`, `JournalMetricsReadModel`, `JournalMaterializer`, `JournalSnapshotReader`, `JournalSyncService`.

## Goals / Non-Goals

**Goals:**

- Переопределить внутренний порядок групп позиций: экспирация от дальней к ближней → страйк от большого к малому → CALL раньше PUT → фьючерсы и прочие неопционные инструменты в конце; открытые перед закрытыми сохраняются.
- Выводить последние сделки в начале в таблице сделок деталей конструкции и во «Входящих».
- Сохранить детерминизм порядка между перечитываниями.

**Non-Goals:**

- Не менять контракт `TradeMaterializer.Materialize` (хронологический порядок остаётся доменным договором для FIFO и материализации экспираций).
- Не менять сортировки вне двух затронутых таблиц: список конструкций, закрывающие записи, корректировки, snapshot подсказок (`JournalSnapshotReader` сортирует позиции по тикеру для своего контракта).
- Без изменений хранения, миграций и API.

## Decisions

- **d1 — сортировка только на границах представления.** Порядок меняется в `ConstructionDetailReadModel` и `InboxReadModel`, доменный материализатор остаётся хронологическим. Альтернатива — развернуть порядок в самом материализаторе — отвергнута: потребители движков полагаются на хронологию, инвертирование потребовало бы правок домена без пользы для поведения.

- **d2 — составной ключ позиций с убывающими компонентами и сентинеллами.** Цепочка: открытость (открытые раньше) → `ExpiryDate` по убыванию → `Strike` по убыванию → ранг типа (CALL=0, PUT=1, прочие=2) по возрастанию → тикер по `StringComparer.Ordinal` как детерминирующий тай-брейк. Неопционные символы получают сентинеллы `DateTime.MinValue` и `decimal.MinValue`, поэтому в убывающих компонентах уходят в конец группы, а ранг 2 закрепляет их после опционов. Альтернатива — отдельный `IComparer` — отвергнута: LINQ-цепочка с явными ключами проще и покрывается тестом на эталонный пример из спецификации.

- **d3 — тай-брейк сделок по execId по убыванию.** `OrderByDescending(ExecutedAt)` затем `ThenByDescending(ExecId, StringComparer.Ordinal)`. При равном времени исполнения порядок фиксирован и воспроизводим; отдельный порядковый номер вставки в проекцию сделки не добавляется — расширение `MaterializedTrade` ради краевого случая не оправдано. Поведение фиксируется в сценарии как детерминизм, а не как «поступившая позже».

## Risks / Trade-offs

- [Неопционный символ в убывающих ключах всплывёт наверх при неверном сентинелле] → тесты фиксируют положение фьючерса последней строкой группы на эталонном примере из спеки.
- [Потребители `InboxReadModel` вне экрана «Входящие» получают изменённый порядок] → возвращаемый тип не меняется; порядок списка — контракт экрана, сценарий спеки закрепляет его; другие вызовы read-модели в коде отсутствуют.
- [Изменится вид существующих экранов без изменения данных] → миграций нет, откат — возврат прежнего порядка ключей.
