# Design

## Context

Списковый контракт `GET /api/v1/chats?status=` (`AgentChatDto`: id, статус, params, createdAt, lastMessageAt) не несёт опознавательных данных; `lastMessageAt` уже вычисляется в API-слое чтением истории каждого чата (`BuildChatDtoAsync`, `AgentEndpoints.cs`). Пункт сессии на форме агентов (`ChatList`/`SessionItem` в `agent-page.tsx`) рендерит модель и время. Имя конструкции фронт может разрешить сам: `fetchConstructionsOverview()` (`lib/api/constructions.ts`) возвращает id и имя. Панель чатов карточки фильтрует по привязке на клиенте и уже применяет fallback `конструкция {id}` при неразрешённом имени.

## Goals / Non-Goals

**Goals:**

- Пункт сессии на форме агентов опознаваем без открытия чата: имя конструкции, превью первого сообщения владельца.
- Свежие чаты вверху своих статусных групп.
- Портфельные и привязанные чаты разделены в обеих статусных группах.

**Non-Goals:**

- Панель чатов карточки не меняется (контекст карточки уже определяет конструкцию); превью в её пункты не выводим.
- Схема БД чатов не меняется; миграций нет.
- Поиск/полнотекстовый поиск по чатам — вне scope.

## Decisions

### D1. Превью вычисляется бэкендом из того же чтения истории, что и lastMessageAt

`BuildChatDtoAsync` уже читает историю каждого чата ради `lastMessageAt`; первое сообщение владельца (минимальный Id с ролью владельца) берётся из той же выборки — стоимость списка не растёт. Поле добавляется в `AgentChatDto` (и в домен-порт представления `ChatRecord`→DTO, где это диктует слоистость) обратно совместимо: новые клиенты используют, старые игнорируют.

Альтернатива — колонка в `Chats` — отклонена: дублирование данных истории требует миграции и синхронизации, а история чата иммутабельна только в сторис-смысле (сообщения только добавляются), первое сообщение владельца никогда не меняется, но и колонка не нужна при дешёвом вычислении.

### D2. DTO несёт полный текст первого сообщения, обрезание — забота UI

Сервер не режет превью лимитом: произвольная константа в контракте усложняет тесты и теряет данные для будущих клиентов. Пункт сессии ужимает превью в одну строку CSS-truncate'ом.

Альтернатива — обрезка на сервере (например, 140 символов) — отклонена: экономия трафика несущественна для малых списков.

### D3. Имя конструкции резолвит фронт из обзора конструкций

`ChatDto` не получает `constructionName`: имя принадлежит агрегату конструкций и меняется переименованием — дублирование в чат-контракте создало бы вторую копию истины. Фронт берёт имя из кэша `fetchConstructionsOverview()` по `params.constructionId`; при неразрешённом id — fallback `конструкция {id}` (как в панели карточки).

Альтернатива — имя в `ChatDto` на бэкенде — отклонена по той же причине.

### D4. Сортировка по свежести — на фронте, контракт бэкенда не меняется

UI сортирует полученный список по `lastMessageAt` по убыванию внутри статусной группы. Порядок бэкенда (`OrderBy Id`) остаётся как есть: API нейтрален к порядку, панель карточки фильтрует клиентски и порядок не использует.

Альтернатива — сортировка в бэкенде — отклонена: потребовала бы вычислять `lastMessageAt` до сортировки на уровне хранилища, тогда как фронтовая сортировка бесплатна на уже готовых DTO.

### D5. Разделение по привязке — подгруппы, не фильтр

Внутри «АКТИВНЫЕ» и «ЗАВЕРШЁННЫЕ» — подгруппы «Портфель» и «Конструкции» с счётчиками; пустая подгруппа показывается с нулевым счётчиком, чтобы разделение было предсказуемым. Фильтр-чипы скрыли бы чаты за кликом и добавили состояние/URL-параметры на форме агентов, где их ещё нет.

## Risks / Trade-offs

- [Списки из десятков чатов: чтение истории на чат] → превью берётся из уже существующего чтения истории, новых запросов к БД на пункт не добавляется; при росте списков порядок `O(chats × history)` станет заметен — тогда перенос `lastMessageAt`/превью в хранилище (D1-альтернатива) будет отдельным change.
- [Первое сообщение владельца отсутствует (битые данные)] → пункт рендерится без превью, опознаваемость деградирует до статуса «до change» без ошибки; вычисление превью толерантно к пустой истории.
- [Неразрешимое имя конструкции (запись удалена мимо стирания чатов)] → fallback `конструкция {id}`, как в панели карточки.
- [Подгруппы удваивают заголовки при малых списках] → нулевые счётчики в заголовках; вёрстка подгруппы не отличается от существующей группы.

## Migration Plan

Добавление поля в DTO обратно совместимо: деплой бэкенда, затем фронта; откат — в любом порядке без миграций.
