# Design

## Context

См. proposal.md — Why. Бэкенд оспаривания развёрнут change `synthetic-close-logical-layer`: эндпоинты `POST /constructions/{id}/synthetic-closes/dispute|revert`, признак `disputed` в `syntheticCloses[]`, споры хранятся в `SyntheticCloseDisputes` и стираются полным пересбором. UI показывает только агрегированную строку «зафиксировано синтетикой» в `ConstructionMetricStrip`; построчного списка связок нет, клиентских функций спора нет.

Ключевой пробел: строка `ConstructionCardSyntheticCloseResponse` не содержит пару `linearExecId`/`counterOptionExecId`, по которой эндпоинты спора ключуют связку. Read-model строит строки из `SyntheticCloseLink`, где эти идентификаторы есть — их нужно пробросить в контракт.

## Goals / Non-Goals

**Goals:**

- Пользователь оспаривает и возвращает связку из карточки конструкции, видимая обратная связь — перечитанная карточка.
- Список связок показывает каждую связку, включая оспоренные, с признаком спора.
- Действие следует существующим паттернам карточки: `useCardCommands` + `invalidate` + `firstError`.

**Non-Goals:**

- Изменение семантики спора на бэкенде (идемпотентность, стирание пересбором) — уже задано `synthetic-close-logical-layer`.
- Массовое оспаривание нескольких связок одним действием.
- Предупреждение о стирании спора пересбором — принято дизайн-решением предыдущего change.

## Decisions

### 1. Контракт карточки дополняется парой execId аддитивно

`ConstructionCardSyntheticCloseResponse` и TS-тип `ConstructionCardSyntheticClose` получают `linearExecId` и `counterOptionExecId` в конец записи — тот же приём аддитивности, что D5 предыдущего change: существующие потребители не ломаются. Read-model уже вычисляет эти поля из `SyntheticCloseLink`. Альтернатива «отдельный эндпоинт чтения ключей связок» отвергнута: лишний round-trip ради данных, которые read-model уже держит.

### 2. Раскрывающийся список — переключатель в строке синтетики

Строка «зафиксировано синтетикой» получает хвостовой переключатель раскрытия (chevron). Под строкой разворачивается компактный список связок: нога, количество, лок, для оспоренной — приглушённый вид с признаком «оспорена», действие «Оспорить»/«Вернуть» в конце строки. Состояние раскрытия — локальный state компонента, не в URL: состояние просмотра, не фильтр. Список рендерится из `card.syntheticCloses` как есть — и оспоренные, и нет.

### 3. Строка-переключатель живёт, пока есть хоть одна связка

Условие показа строки меняется с «есть неоспоренные связки» на «есть распознанные связки» (`syntheticCloses.length > 0`): когда все связки оспорены, строка остаётся свёрнутым переключателем без величины лока и логического размера ноги — возврат остаётся достижим (сценарий `scenario-dispute-list-available-when-all-disputed`). Величины в строке считаются только по неоспоренным связкам, как сейчас. Альтернатива «прятать строку целиком» отвергнута — теряется путь возврата.

### 4. Команды спора идут через `useCardCommands`

Две мутации (`disputeSynthetic`, `revertSynthetic`) с `mutationFn` из новых клиентских функций и `onSuccess: invalidate` — карточка перечитывается целиком, логический слой пересчитывается сервером при чтении. Без оптимистичных обновлений: агрегаты строки и распад ноги считаются из снимка, двойное вычисление на клиенте дублировало бы read-model. Ошибки (404 спора при возврате, 400) показываются через `firstError` у шапки, как у прочих команд. Идемпотентность оспаривания и 404 неоспоренной связки при возврате обрабатываются сервером — клиент не маскирует их повторами.

### 5. Визуальный источник — design.pen, приёмка скриншот-сверкой

По ADR-0011 мастер списка связок добавляется в design.pen рядом с мастером сводки (Z5uVG/h69OG из предыдущего change): строка-переключатель, раскрытый список, оспоренная строка. Компонент собирается из примитивов `ui/design-system`.

## Risks / Trade-offs

- [Контракт растёт на два поля в строке связки] → аддитивно в конец записи; контрактный тест предыдущего change приёмку не ломает.
- [Перечитывание карточки целиком на каждый спор] → снимок один, ответ лёгкий; частота ручного оспаривания не создаёт нагрузки.
- [Расхождение design.pen и реализации] → скриншот-сверка в задачах, приёмка визуального оформления.

## Migration Plan

Изменение только кода и контракта чтения: деплой атомарен (клиент и сервер едят одни поля), откат — откат релиза; данных и миграций нет.
