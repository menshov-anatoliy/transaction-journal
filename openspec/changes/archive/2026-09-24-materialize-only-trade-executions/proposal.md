# Proposal

## Why

Разовая сверка живой `journal.db` с официальной CSV-выгрузкой Bybit AssetChangeDetails (change `reconcile-bybit-statement`, issue #17) показала: из 1833 сырых записей исполнения в диапазоне выгрузки 700 — записи `execType: "Funding"` из истории исполнения linear-категории. Материализация `TradeMaterializer.Materialize` трактует каждую сырую запись как сделку, поэтому фандинг попадает во «Входящие» как 700 фиктивных сделок с количеством и ценой по марк-цене: их можно привязать к конструкциям, и они искажают позиции, метрики и PnL-аналитику. Хранение таких записей в сырье правомерно — требование «Необработанные записи хранятся целиком» — ошибочен только вывод сделки из не-Trade записи.

## What Changes

- Материализация сделки «Входящих» выполняется только для сырых записей исполнения с биржевым `execType = "Trade"`; записи прочих типов (Funding и любые другие не-Trade значения биржи, включая пустое или неизвестное значение) не становятся сделками и не дают ошибок или предупреждений.
- Фильтр применяется в единственной точке вывода сделок — `TradeMaterializer` — и потому автоматически действует во всех потребителях проекции: «Входящие», таймлайны позиций, метрики журнала, детали конструкции и расчёт остатков для закрывающих записей экспираций.
- Сырые записи не-Trade типов продолжают храниться целиком и остаются доступны для переразбора и диагностической сверки; фильтрация при загрузке синхронизацией не вводится.
- Применение правила к уже загруженным данным выполняется штатным переразбором сырых записей (команда «Переразобрать» на экране «Настройки»): 700 фандинг-записей живой базы исчезнут из «Входящих» без миграций и без обращения к бирже.
- Тестовые фикстуры сырых записей дополняются явным `execType`, появляются тесты: Funding-запись не материализуется в сделку, прочие не-Trade типы не материализуются, Trade-записи материализуются как прежде.
- Фандинг не получает собственного доменного представления (запись начисления, статья PnL) — это осознанное ограничение области: журнал сделок остаётся журналом сделок.

## Capabilities

### New Capabilities

- (нет)

### Modified Capabilities

- `sync/bybit-history`: требование «Новые записи попадают во «Входящие»» уточняется — сделкой «Входящих» становится только запись исполнения с `execType = "Trade"`; добавляется требование о видимом поведении записей прочих типов исполнения: они хранятся в сырье, не становятся сделками и не считаются ни одним из доменных представлений.

## Impact

- `src\TransactionJournal\Materialization\TradeMaterializer.cs` — единственная точка фильтра по `execType`; контракты результата (`TradeMaterializationResult`, `MaterializedTrade`) не меняются.
- Косвенно — `ExpiryMaterializer` (остатки и денежный поток по сделкам), `InboxReadModel`, `PositionReadModel`, `JournalMetricsReadModel`, `ConstructionDetailReadModel`: поведение меняется только в части исключения не-Trade записей, правки кода в них не требуются.
- `tests\TransactionJournal.Tests` — фикстуры payload-хелперов получают явный `execType: "Trade"`, новые тесты фильтра в `Materialization` и доменных read-моделях.
- Схема БД, синхронизация загрузки, публичные API, UI — без изменений; живая база применяется новое правило штатным переразбором.
