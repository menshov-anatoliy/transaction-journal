# Design

## Context

Поставщик учётных данных `EnvironmentBybitCredentialsProvider` читает `BYBIT_API_KEY`/`BYBIT_API_SECRET` из переменных процесса (`Environment.GetEnvironmentVariable`) — это dev-решение из D6 архивированного change `add-bybit-sync`, место хранения секрета определял [#4](https://github.com/menshov-anatoliy/transaction-journal/issues/4). Единственная точка входа — `Program.cs`: сначала веб-приложение, позже там же планируется раннее ветвление режима `--mcp` (change `add-mcp-server`). `.gitignore` уже содержит паттерн `.env` (шаблон `dotnet new gitignore`), файла `.env` в репозитории нет. См. proposal.md — Why.

## Goals / Non-Goals

**Goals:**

- Значения из `.env` попадают в переменные процесса до первого чтения любым потребителем (сейчас — поставщик ключа Bybit).
- Системные переменные окружения сохраняют приоритет над `.env`.
- Логика загрузки покрыта модульными тестами по стилю проекта (NUnit + MSTest-атрибуты, очистка окружения в Initialize/Cleanup).
- Загрузка выполняется до ветвления режимов exe — будущий режим `--mcp` получает её автоматически.

**Non-Goals:**

- Не пересматривается решение [#4](https://github.com/menshov-anatoliy/transaction-journal/issues/4) о постоянном месте хранения секрета: `.env` — дополнительный локальный источник, а не замена; системные переменные работают как раньше.
- Не переключается провайдер на `IConfiguration`/имена `Bybit__ApiKey` — контракт поставщика не меняется.
- Не добавляется UI для ввода ключей и шифрование `.env` — read-only ключ персонального локального инструмента.

## Decisions

### D1. Загрузка пакетом DotNetEnv

Выбор владельца. Альтернативы: собственный парсер (поддержка кавычек, комментариев, экранирования своими силами — код ради кода) и самописный провайдер `Microsoft.Extensions.Configuration` (та же работа парсера плюс инфраструктура провайдера). `DotNetEnv` закрывает потребность одной строкой: флейнт-API `Env.TraversePath().NoClobber().Load()` даёт поиск вверх по дереву и приоритет существующих переменных; отсутствующий файл возвращает пустую последовательность без исключений.

### D2. Точка загрузки — самое начало Program.cs

Вызов до `WebApplication.CreateBuilder` и любых регистраций. Ключ читается лениво (в момент синхронизации), но ранняя загрузка гарантирует порядок для любого будущего потребителя и срабатывает до ветвления режимов web/`--mcp`. Альтернатива — ленивая загрузка внутри поставщика — привязала бы поставщика к файловой системе и усложнилала его тесты, не давая преимуществ.

### D3. Обёртка `AppEnvFile` вместо прямого вызова в Program.cs

Статический класс в корне проекта (`src/TransactionJournal/AppEnvFile.cs`, namespace `TransactionJournal`) с методом `Load()`, инкапсулирующим `DotNetEnv.Env.TraversePath().NoClobber().Load()`. Program.cs остаётся декларативным, а логика загрузки получает тестовое место: тесты создают временный каталог с `.env`, переключают текущий каталог, проверяют результат и восстанавливают окружение. Альтернатива — прямой вызов в Program.cs — не тестируется без запуска всего приложения.

### D4. Поиск вверх от текущего каталога, системные переменные без перезаписи

`NoClobber` — реализует требование приоритета системы (spec: `requirement-system-vars-take-precedence`): значение из файла применяется только к незаданным переменным. `TraversePath` — `.env` находится и при `dotnet run` из `src/TransactionJournal` (файл в корне репозитория), и при запуске из корня; побеждает ближайший к текущему каталогу файл, что защищает от случайного подхвата внешнего `.env` при его наличии nearer. Отсутствие файла — штатный путь (spec: `scenario-missing-env-file-is-normal`).

### D5. Шаблон `.env.example` в корне репозитория

Файл с `BYBIT_API_KEY=` и `BYBIT_API_SECRET=` и заглушками-плейсхолдерами, с комментариями на русском о назначении и приоритете системных переменных. Паттерн `.gitignore` совпадает только с точным именем `.env`, поэтому `.env.example` коммитится свободно, а реальный `.env` остаётся игнорируемым (spec: `requirement-env-file-stays-local`). Документация использования живёт в самом шаблоне — отдельного README о запуске в проекте нет.

### D6. Поставщик учётных данных не меняется

`EnvironmentBybitCredentialsProvider` читает переменные процесса — после загрузки `.env` значения уже на месте, контракт и существующие тесты сохраняются. Новые тесты проверяют связку «`.env` → переменные процесса → `GetCredentials()`» на уровне обёртки `AppEnvFile`, без изменения продакшн-кода поставщика.

## Risks / Trade-offs

- [Запуск опубликованного exe из произвольного каталога: `.env` в корне репозитория не найден] → Документируем в `.env.example` размещение «рядом с exe или выше по дереву от рабочего каталога»; системные переменные остаются рабочим fallback-путём [#4](https://github.com/menshov-anatoliy/transaction-journal/issues/4).
- [Загрязнение переменными между тестами обёртки] → Тесты восстанавливают текущий каталог и удаляют переменные в Initialize/Cleanup — паттерн уже принят в `EnvironmentBybitCredentialsProviderTests`.
- [Новая зависимость в цепочке поставок] → Пакет миниатюрный и широко используемый, вызывается один раз при старте; версия фиксируется в `TransactionJournal.csproj`.
- [Случайный коммит реального `.env`] → Паттерн `.env` уже в `.gitignore`; шаблон содержит только заглушки.

## Migration Plan

Изменение аддитивное: один ранний вызов в `Program.cs`, новый класс, новый файл шаблона. Откат — удалить вызов `AppEnvFile.Load()` и пакет; поведение возвращается к текущему (только системные переменные).
