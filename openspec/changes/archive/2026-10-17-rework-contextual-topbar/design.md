# Design

## Context

Каркас SPA сегодня (`frontend/src/components/layout/AppLayout.tsx` после `rework-panel-collapse-footer`, заархивирован 2026-10-16 как superseded этапом сверки): тонкий топбар 54 px (бренд + компактный итог журнала), левая и правая панели с футерами сворачивания, свёрнутые панели — рейка миниатюр над футером. design.pen — источник истины (ADR-0011): на стенде «Стенд/Концепции каркаса» (WufvO) рассмотрены v0 и К1–К4; владелец принял **К1 «Контекстный топбар»** и синхронизировал его на мастер-каркас g0z20 и все экраны (коммит «Синхронизация выбранного дизайна на все формы design.pen»). Мастер-топбар jGvOM: высота 64 px, сегмент навигации 240 px (= ширине «Панель/Навигация» t4nFb), сегмент страницы fill, сегмент контекста 360 px (= ширине «Панель/Контекст» gPp4K); в «Ряде каркаса» GkCUh футеров нет; «Схема состояний панелей» Yh0Wo: развёрнута/свёрнута — кнопка управления в заголовке сегмента, свёрнута — рейка миниатюр на всю высоту. Легенда стенда фиксирует состав контекстного заголовка: из панели навигации — крошка и счётчик входящих; из центральной зоны — заголовок и ключевые действия страницы; из контекстной панели — что открыто; сквозное — итог журнала и статус синхронизации. Экраны ссылаются на мастер-топбар без переопределений — состав сегмента «страница» на каждом экране выводится по легенде в раундах-сверках форм.

Решения сессии планирования (grill, 2026-10-16): один change на весь перенос; ADR-0016; статус синхронизации — последний успешный запуск, пусто/сбой — скрыт; бейдж «Входящих» — и в меню, и у крошки (решение владельца); чип контекста — label из регистрации без клика; Mobile — последней стадией; DoD формы — скриншот-сверка + тесты + traceability; перед каждой формой — раунд-сверка.

## Goals / Non-Goals

**Goals:**

- Каркас по К1: сегментный топбар 64 px, жёстко выровненный по колонкам; футеры панелей удалены; свёрнутость управляется из топбара.
- Механика поставки контента в сегменты: регистрация шапки страницы (Outlet-контекст), label контекста, сквозные итог и статус синхронизации.
- Поэтапный перенос всех форм design.pen в новом каркасе с приёмкой по ADR-0011 на каждой.

**Non-Goals:**

- Мобильная механика до стадии Mobile (drawer-шторка не меняется).
- Персистентность геометрии панелей, диапазоны ширин (4.25–20 / 20–40 rem), поведение «без контекста панель скрыта».
- Клик по чипу контекста и по статусу синхронизации — не проектируются.
- Попиксельный перфект (ADR-0011: токенно-компонентное соответствие).

## Decisions

- **D1 — Сегментный топбар, выровненный по колонкам.** Единый `header` высотой 64 px (`border-b border-divider bg-surface`) с тремя внутренними зонами: левая ширины `left.collapsed ? 2.75rem : left.width` rem, правая ширины `right.collapsed ? 2.75rem : right.width` rem (те же значения, что у `aside` панелей — визуальная колонка продолжается в топбар), центральная `flex-1`. Паддинги сегментов по мастеру: навигация/контекст [0,16], страница [0,20]. Реализация держит ширину в одном месте (значение геометрии панели), чтобы сегмент и панель не разъехались. Альтернатива «независимый топбар без привязки к панелям» отклонена: К1 строится именно на выравнивании по колонкам.
- **D2 — Сегмент навигации.** Развёрнутая панель: лого-глиф + «Журнал Bybit» + spacer + ghost icon-кнопка сворачивания у внутреннего (правого) края. Свёрнутая: сегмент сжат до 44 px (`px-1`), лого и бренд скрыты, внутри только кнопка разворачивания. `aria-label`/`title` сохраняются.
- **D3 — Сегмент страницы и регистрация шапки.** Новый контракт Outlet-контекста (по образцу `ContextPanelApi`): страница может зарегистрировать `{ title?, chips/actions }`; крошка всегда «Журнал / <раздел>» из `appSections`, бейдж «Входящих» у крошки (тем же запросом `inbox-count`, что и пункт меню). Без регистрации сегмент показывает крошку и заголовок раздела из `appSections`. Правая часть сегмента — инварианты каркаса: итог журнала с разбивкой (`JournalTotal`, сценарий сбоя марок сохраняется) и статус синхронизации (D5); они видны на любом экране и не регистрируются страницами.
- **D4 — Сегмент контекста.** Существует только при зарегистрированном контексте. `ContextPanelRegistration` расширяется обязательным коротким названием (`chipLabel`): развёрнутая панель — кнопка сворачивания у внутреннего (левого) края + чип `chipLabel` (токены чипа по дизайн-системе, цвет `$info` по мастеру bOfzl/s5fwGV); свёрнутая — сегмент 44 px, только кнопка разворачивания. Клик по чипу не проектируется. Без регистрации контекста панель и сегмент скрыты, сегмент страницы занимает всю ширину.
- **D5 — Статус синхронизации.** «Обновлено HH:MM» из `fetchSyncRuns` (последняя запись со статусом `succeeded`), время — в часовом поясе браузера (существующий слой форматирования). Пустой журнал, отсутствие успешных запусков или ошибка загрузки — блок (иконка + текст) скрыт; деградации остальных элементов топбара нет. Клик не проектируется.
- **D6 — Панели без футеров.** `PanelFooter.tsx` удаляется; `PanelMiniatureRail` занимает всю высоту панели свёрнутого состояния (прокрутка при переполнении сохраняется, миниатюры — те же). Отступы контента развёрнутых панелей не меняются (левая `px-3 py-4`, правая `px-3 pt-3.5 pb-3`). `COLLAPSED_LEFT_WIDTH_REM = 2.75` сохраняется.
- **D7 — Спека.** `requirement-app-frame-navigation`: сценарий `scenario-frame-collapse-button-in-panel-footer` заменяется на `scenario-frame-collapse-button-in-topbar-segment`; `scenario-frame-collapsed-panel-miniature-rail` переписывается (рейка на всю высоту, без футера);добавляются сценарии: выравнивание сегментов по колонкам, регистрация шапки страницы, статус синхронизации, чип контекста; `scenario-inbox-badge-counts-unassigned` дополняется бейджем у крошки. `requirement-design-frame-resizable-panels` переписывается под К1 (сценарий футера заменяется сегментным). Ссылки в коде/тестах на удалённые ID заменяются в той же правке.
- **D8 — Процесс переноса форм.** Перед каждой формой — раунд-сверка с владельцем (предлагаю состав сегмента «страница» этой формы по макету и легенде, отличия от текущего frontend); после — реализация, скриншот-сверка через MCP pen с записью результата в tasks.md, зелёные точечные тесты, traceability-метки. Порядок: Каркас → Конструкции → Карточка конструкции → Входящие → Подсказки → Агент · Чаты → Агент · Чат активный → Агент · Правила → Синхронизация → Mobile · Конструкции, Mobile · Агент · Чат.
- **D9 — design.pen.** Не правится (уже источник истины К1); исключение — нестыковки, всплывшие в раундах-сверках форм: тогда правка дизайна вперёд, затем переноса (ADR-0011).

## Risks / Trade-offs

- [Сегмент страницы перегружен на средних ширинах (крошка+заголовок+чипы+итог+статус)] → инварианты (итог, статус) не скрываются никогда; чипы страницы — на усмотрение раунда-сверки формы; при нехватке места шина решается в раунде конкретной формы.
- [localStorage хранит свёрнутость от версии с футерами] → миграция не нужна: ключи геометрии не меняются, нормализация ширин уже существует.
- [Ссылки на удалённый сценарий footer в коде и тестах] → замена ID в той же правке (прецедент: `rework-panel-collapse-footer`, D7 Risks).
- [Крошка + бейдж дублируют информацию пункта меню] → принято владельцем осознанно (бейдж в обоих местах).

## Migration Plan

1. Стадия «Каркас» (tasks 1.x): сегментный топбар, удаление футеров, регистрации, статус синхронизации; сверка с мастером g0z20.
2. Формы по одной (tasks 2–10): раунд-сверка → реализация → сверка/тесты/traceability.
3. Финальная приёмка: полный прогон тестов frontend и скриншот-сверка всех экранов.

Отката не требуется: изменение UI-структуры каркаса, данные и API-контракты не затронуты.
