# Design

## Context

Стек и режим зафиксированы картой ([#1](https://github.com/menshov-anatoliy/transaction-journal/issues/1)): C#/.NET, EF Core + SQLite, Blazor Server, локальный инструмент одного пользователя. Доменная семантика — CONTEXT.md и ADR-0001/ADR-0002 после гриллинга edge-cases ([#5](https://github.com/menshov-anatoliy/transaction-journal/issues/5)): сделка = одно исполнение, позиция — производный остаток, перенос сделок свободен, всё производное пересчитывается при чтении. Синхронизация (change `add-bybit-sync`, тикет [#8](https://github.com/menshov-anatoliy/transaction-journal/issues/8)) материализует сделки во «Входящие» и выводит закрывающие записи экспираций из сырых биржевых записей; этот change — приёмник этих данных. Аналитика (PnL, метрики) — отдельная capability (тикет [#10](https://github.com/menshov-anatoliy/transaction-journal/issues/10)).

## Goals / Non-Goals

**Goals:**

- Единственный мутируемый агрегат — конструкция и пользовательские записи к ней; позиции и результаты — производные.
- Пользовательские данные хранятся по стабильным ключам (`execId` сделки; «конструкция × инструмент» для позиции) и переживают переразбор и пересчёт.
- Инвариант «сделка ровно в одной конструкции» на всех операциях привязки.
- Слой доменных операций, достаточный для UI ([#12](https://github.com/menshov-anatoliy/transaction-journal/issues/12)) и MCP ([#11](https://github.com/menshov-anatoliy/transaction-journal/issues/11)).

**Non-Goals:**

- Расчёт реализованного/нереализованного PnL, метрики — capability аналитики ([#10](https://github.com/menshov-anatoliy/transaction-journal/issues/10)).
- Автоподсказки привязки сделок (туман карты).
- Версионирование и аудит правок — нет в MVP (решение [#5](https://github.com/menshov-anatoliy/transaction-journal/issues/5)).
- Funding, конверсия валют, торговые операции — вне скоупа усилия.

## Decisions

### D1. Конструкция — единственный мутируемый агрегат; остальное выводится

Пользовательские записи: `Construction` (имя, статус, выделенный капитал, комментарий), `TradeUserdata` по `execId` (привязка, комментарий), `PositionComment` по «конструкция × инструмент», `ManualCloseMark` (конструкция, инструмент, цена, время), `PnLAdjustment` (дата, источник «робот»/«ручная», знаковая сумма, комментарий). Позиции, остатки и закрывающие записи экспираций вычисляются из сделок материализатора sync плюс пользовательских записей при чтении. Согласовано с `add-bybit-sync` D3: всё производное пересчитывается, перепривязка не требует синхронной правки производных.

Альтернатива: материализованные строки позиций с синхронной правкой при перепривязке — отклонена: порождает рассинхрон (тот же аргумент, что и в sync D3).

### D2. Комментарий позиции — по ключу «конструкция × инструмент»

Позиция производная и собственной строки не имеет; комментарий хранится по ключу и переживает закрытие, переоткрытие и пересчёты. Единственный способ соблюсти «комментарий на позиции» без мутируемой сущности.

### D3. Ручная пометка закрытия — пользовательская закрывающая запись

`ManualCloseMark` (конструкция, инструмент, цена, время) применяется в производном слое как закрывающая запись с количеством, равным остатку на момент применения по хронологии. Правка и удаление свободны — пересчёт автоматически «открывает» позицию обратно. Цена по умолчанию — последняя известная марка инструмента (кэш марок — контракт со слоем синхронизации/аналитики).

### D4. Статус конструкции — перечисление с ручным управлением

Статусы: открыта, закрыта, архив. Смена свободна; архивация скрывает конструкцию из активных списков, оставляя её в аналитике. Автоматического статуса нет — решение гриллинга [#5](https://github.com/menshov-anatoliy/transaction-journal/issues/5).

### D5. Операционный слой — тонкие use-case сервисы

Сервисы управления конструкциями, привязками, корректировками, пометками и комментариями поверх EF Core; чтение — `PositionReadModel` (производный запрос остатков). UI и MCP используют одни и те же сервисы; MCP ограничен чтением через read-модели.

### D6. Граница с add-bybit-sync

Sync материализует сделки и их атрибуты и кладёт новые во «Входящие»; общий ключ — `execId`. Домен владеет привязками и пользовательскими записями. Закрывающие записи экспираций (delivery/OTM) выводятся sync-слоем из сырых delivery-записей; ручные пометки — записи домена; `PositionReadModel` сливает оба вида в единый поток закрывающих записей.

## Risks / Trade-offs

- [Производные вычисления при каждом чтении] → объёмы персонального журнала малы; при росте — кэш вычислений, не меняющий контракт (тот же риск, что и в sync).
- [Ручная пометка при поздно пришедшей delivery] → обе записи претендуют на обнуление остатка; вторая по хронологии становится избыточной — отражается предупреждением сверки, не блокирует.
- [Пустая конструкция с осиротевшими пометками/комментариями позиций] → условие удаления «без сделок и корректировок» на практике исключает живые пометки; оставшиеся записи удаляются каскадом вместе с конструкцией.
- [Нет аудита правок корректировок и пометок] → осознанное ограничение MVP ([#5](https://github.com/menshov-anatoliy/transaction-journal/issues/5)).

## Migration Plan
