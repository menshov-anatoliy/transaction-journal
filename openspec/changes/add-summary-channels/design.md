# Design

## Context

Движок и хранение подсказок готовы change'ом `add-hints-engine`; канал, каденция и формат утверждены: [#21](https://github.com/menshov-anatoliy/transaction-journal/issues/21) (Telegram-бот, 3 прохода/день в окне, буферизация, недоступность рынка), [#34](https://github.com/menshov-anatoliy/transaction-journal/issues/34) (5-секционный скелет, группы v1, чек-лист, эфемерность, граница LLM), [#31](https://github.com/menshov-anatoliy/transaction-journal/issues/31) (критерии готовности и приёмка владельцем). ADR-0007 фиксирует механику: hosted BackgroundService, `IChatClient` с JSON-режимом и шаблонной деградацией, инструкции агента файлом.

## Goals / Non-Goals

**Goals:**

- Hosted BackgroundService: 3 автопрохода в настраиваемом окне, ручной `/summary` всегда.
- Telegram-бот long-polling: push-сводки, `/summary`, `/status` (без LLM), без пишущих команд.
- Сборка сводки по скелету #34 с группами v1 и буферными маркерами; LLM-изложение тел секций с JSON-схемой и деградацией до шаблона.

**Non-Goals:**

- Срезы корпуса v2, подсказки входа v2, метрики качества, R3-сессия, `--hints-once` CLI, MCP-сервер ADR-0003 ([#31](https://github.com/menshov-anatoliy/transaction-journal/issues/31)).
- Хранение текстов сводок и история доставок: сводка эфемерна, хранятся только подсказки.
- Синхронизация журнала из агента: проход только читает ([#21](https://github.com/menshov-anatoliy/transaction-journal/issues/21)).

## Decisions

### D1. Один проход — один конвейер: сборка → изложение → доставка

Проход (плановый или ручной) выполняет тот же `HintAgentPass`, что в change `add-hints-engine`: валидность корпуса → снимок → журнал → марки → подсказки. Сводка собирается кодом в структурированный скелет (секции с готовыми строками подсказок), затем тела секций излагает LLM, затем канал доставляет. Деградация любой ступени (LLM, канал) не отменяет предыдущие: подсказки уже зафиксированы, буфер маркеров обновится доставкой.

### D2. Планировщик — BackgroundService, слоты не догоняются

`SummaryScheduler : BackgroundService` в Hints вычисляет ближайший слот из настройки (3 времени: начало/середина/конец дня) внутри окна активности и спит до него; вне окна — спит до открытия окна. Пропущенный по простою слот пропускается без навёрстывания; маркер «включая N пропущенных проходов» выводится из счётчика невыполненных слотов между доставками. Планировщики ОС и Hangfire отклонены в [#22](https://github.com/menshov-anatoliy/transaction-journal/issues/22) — in-app таймера достаточно.

### D3. Telegram — long-polling в том же exe

`TelegramGateway` в Hints поверх Bot API long-polling (без webhook: exe локальный, внешний адрес не нужен). Порт `ISummaryChannel` (отправка сообщений с разбивкой по секциям) изолирует Telegram от сборщика сводки; `/summary` и `/status` — команды того же шлюза. Токен бота и chat id — настройка; доступы готовятся тикетом [#35](https://github.com/menshov-anatoliy/transaction-journal/issues/35). Бот read-only: любые команды, кроме `/summary` и `/status`, игнорируются.

### D4. Сборщик сводки — детерминированный код поверх read-модели подсказок

`SummaryComposer` строит скелет #34: заголовок (тип прохода + as-of две строки, локальный пояс exe), портфельная секция, секции конструкций по группам v1 (порядок фиксирован, пустые скрыты), чек-лист (полный/счётчик по типу прохода), рыночный блок (baseCoin открытых конструкций: underlyingPrice, фандинг), футер (шаблон: метка движка/статус изложения). Полный набор живых `new` подсказок; «+M новых» — от lastDeliveredAt; счётчик пропущенных проходов — от него же. Чек-лист и «непокрытые кодом» правила — из снимка корпуса (implementation null/unknown). Разбивка длинных сообщений — по границам секций, лимит Telegram учитывается; при экстремальном объёме — свёртка секции конструкций до имён с числом.

### D5. LLM — IChatClient, JSON-режим, двойная попытка

`NarrationService` вызывает `IChatClient` один раз за проход: вход — инструкции агента (файл `agent-prompt.md` или встроенный дефолт) + тела секций как факты; выход — JSON по схеме (секции с тем же составом строк). Валидация схемы: retry один раз, затем шаблонное изложение (те же секции списками). Состояние последнего изложения (LLM/шаблон) сохраняется для `/status`. Провайдер — конфигурация (`Microsoft.Extensions.AI`, дефолт z.ai GLM-5.3-Flash; смена — ключ/URL без кода). Заголовок с as-of и футер модель не излагает никогда.

### D6. Эфемерность и буфер — маркеры, а не хранение

Хранятся только факты: `lastDeliveredAt` (время последней успешной доставки) и счётчик невыполненных слотов. Тексты сводок нигде не пишутся; повторная доставка тех же текстов невозможна — каждый проход рендерит текущую картину. Буферизация переживает и недоступность LLM (шаблон), и недоступность канала (маркеры в первой успешной доставке).

## Risks / Trade-offs

- [Long-polling блокирует поток] → Отдельный Task в BackgroundService с cancellationToken; shutdown корректно завершает poll.
- [Лимит Telegram 4096 символов на сообщение] → Разбивка по секциям (D4); экстремальные случаи — свёртка, не обрезка.
- [Нестабильный прайс z.ai / недоступность] → Деградация текста без потери функции; локальная Ollama — сменой конфигурации.
- [Спящий exe (машина выключена на слот)] → Слоты не догоняются — принято [#21](https://github.com/menshov-anatoliy/transaction-journal/issues/21); маркер сообщает о пропусках.
- [Приёмка субъективна] → Критерий из [#31](https://github.com/menshov-anatoliy/transaction-journal/issues/31): живая сверка владельцем сводки с ручным разбором портфеля.

## Migration Plan

Добавление hosted-сервиса, шлюза и настройек к готовому движку; настроек без значений (токен, chat id, провайдер) — агент не доставляет, пока не заполнены ([#35](https://github.com/menshov-anatoliy/transaction-journal/issues/35)). Откат — выключение фича-флага/настроек; движок и UI не затрагиваются.
