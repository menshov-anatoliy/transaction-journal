# Design

## Context

Реальный риск конструкции уже считается агрегатом (`RealRiskCalculator`): группы `(BaseCoin, экспирация)`, перпы прикрепляются к группе ранней экспирации, статус `unbounded` ловит только верхний хвост. Владельцу нужна проноговая диагностика по своим торговым правилам: фьючерсы всегда закрываются опционами конструкции, опционы могут оставаться незакрытыми. В grilling-сессии 2026-10-18 утверждено: единый уровень серьёзности — только предупреждения (категория «ошибка» отклонена; матрица сценариев A–I проверена владельцем), термин неограниченного вкуса — «Риск не ограничен», расчёт на лету без хранения, покрытие по всем открытым опционам того же базового актива независимо от экспирации, отображение в трёх точках (бейдж списка, краткая карточка, основная карточка) с сохранением бейджа «∞».

## Goals / Non-Goals

**Goals:**

- Вычислитель проноговой атрибуции незакрытых рисков: алгебра наклонов на хвостах, приоритет покрытия фьючерсов, частичное покрытие в контрактах, русские тексты с причиной.
- Аддитивные поля в контрактах списка, превью и карточки; бейдж «⚠ N» в строке, полные перечни в краткой и основной карточках.

**Non-Goals:**

- Категория «ошибка» и двухуровневая серьёзность — отклонено владельцем.
- Хранение и история предупреждений: диагностика всегда отражает текущие открытые остатки.
- Изменение группировки или статусов реального риска (`analytics/performance` не затрагивается).
- Включение предупреждений в Telegram-сводки `add-summary-channels` — отдельное решение.
- Блокирующая логика: предупреждения ничего не запрещают.

## Decisions

### D1. Отдельный вычислитель, не расширение RealRiskCalculator

`ConstructionRiskDiagnosticsCalculator` в `Application/Analytics` рядом с `RealRiskCalculator`, вход — тот же список `PositionMetrics` (остатки со знаком, средние цены не нужны). Переиспользуются `OptionSymbolParser`/`LinearSymbolParser`. Не расширяем `RealRiskCalculator`, потому что правила группировки различаются: реальный риск прикрепляет перп к группе ранней экспирации, диагностика агрегирует наклоны по базовому активу через все экспирации.

### D2. Алгебра наклонов на хвостах с приоритетом фьючерсов

По каждому базовому активу на каждом хвосте считаются наклоны: нижний — длинные фьючерсы (+1 за контракт) против длинных путов (−1 ниже страйка); верхний — короткие фьючерсы (−1) против длинных коллов (+1 выше страйка). Покрытие распределяется детерминированно: встречные длинные опционы сначала закрывают фьючерсную часть (торговое правило владельца), остаток наклона коротких опционов закрывается встречными длинными опционами и фьючерсами. Незакрытый остаток фьючерса даёт предупреждение с числом контрактов («1 из 2») и причиной: шорт — «убыток не ограничен», лонг — «убыток ограничен ценой входа»; незакрытый короткий опцион — «убыток не ограничен» (колл) либо «убыток ограничен нулём цены» (пут). Длинные опционы без встречной ноги не предупреждаются: убыток ограничен премией. Короткий пут закрывается коротким фьючерсом, короткий колл — длинным (симметрия наклонов, сценарии `scenario-short-futures-covers-short-put`, `scenario-covered-call-warns-futures-only`).

### D3. Единый уровень серьёзности

Только предупреждения. Исходная идея «фьючерс не закрыт → ошибка» переквалифицирована владельцем в grilling-сессии (матрица A–I): включая неограниченные случаи. Терминология: «Предупреждения конструкции» (механизм), «Риск не ограничен» (неограниченный вкус, переиспользуется из реального риска), отдельные термины по типу ноги не вводятся — вкус ноги живёт в тексте записи.

### D4. На лету при чтении, без хранения

Вычислитель вызывается из `ConstructionMetricsCalculator` тем же проходом, что и реальный риск; в `ConstructionMetrics` попадает счётчик, коллекция записей — в контракты превью и карточки. Ничего не пишется в БД, миграций нет; предупреждения не переживают пересборку и всегда соответствуют текущим открытым остаткам. Конструкция без открытых остатков — пустой набор.

### D5. Контракты API — аддитивно

В `ConstructionListItem` (список и превью) добавляется счётчик предупреждений; в `ConstructionDetailData` — коллекция записей `{ текст }`. Существующие поля (включая `realRiskStatus`, бейдж «∞») не меняются; источник один — тот же вызов вычислителя, что исключает расхождение счётчика бейджа и перечня карточки.

### D6. Сначала макет design.pen, затем перенос во frontend

Изменения UI идут по цепочке «макет → перенос → сверка» (`.github/instructions/design-first.instructions.md`, ADR-0011). Сначала в design.pen через MCP Pen вносятся: бейдж-счётчик «⚠ N» в строке экрана «Конструкции» (паттерн бейджа живых подсказок «✦ N», тон `--risk`), полный перечень предупреждений в краткой карточке контекстной панели и секция «Предупреждения» над таблицами карточки (паттерн секции закрывающих записей) — включая скрытые состояния при пустом наборе. Затем элементы переносятся во frontend с токенно-компонентным соответствием; приёмка — скриншот-сверка живой страницы с макетом. Бейдж «∞» индикатора финрезультата сохраняется: он про агрегатный статус, предупреждения — про ноги.

## Risks / Trade-offs

- [Атрибуция в смешанных случаях (шорт-перп + шорт-колл при дефиците покрытия) неоднозначна] → Детерминированный приоритет: длинные опционы сначала закрывают фьючерсы (D2) — следует торговому правилу владельца; задокументировано сценарием.
- [Неразборчивый символ открытого остатка] → Отдельное предупреждение «покрытие не проверено», не маскирующее остальные проверки (как `unavailable` в реальном риске, но на уровне ноги).
- [Нижний хвост математически ограничен нулём цены] → Осознанное расхождение со статусом `unbounded`: диагностика живёт по торговому правилу владельца, а не по математической неограниченности; лонг-фьючерс без путов предупреждается с причиной «ограничен ценой входа».
- [Расхождение бейджа и перечня] → Один источник: единый вызов вычислителя для списка, превью и карточки (D5).
- [Макет design.pen — источник истины UI] → Порядок «сначала design.pen, затем frontend» (`design-first`-инструкция, ADR-0011): бейдж и секции сначала вносятся в макет через MCP Pen по существующим паттернам, затем переносятся; приёмка — скриншот-сверкой.

## Migration Plan

Чисто аддитивно: новый вычислитель, поля контрактов, UI-элементы. Миграций БД и изменений существующих контрактов нет; откат — скрыть бейдж и секции. Правка макета design.pen — первая задача UI-блока; изменения frontend выполняются только после неё. Глоссарий уже дополнен терминами «Предупреждения конструкции» и «Покрытие фьючерса опционами».
