# Design

## Context

Журнал создаётся с нуля: спек проекта пусты, кодовой базы ещё нет, стек зафиксирован картой ([#1](https://github.com/menshov-anatoliy/transaction-journal/issues/1)): C#/.NET, EF Core + SQLite, Blazor Server. Фактическая основа по Bybit V5 API — исследование `docs/research/bybit-api.md` (ветка `research/bybit-api`): эндпоинты, окна, пагинация, лимиты, авторизация. Доменные правила — CONTEXT.md и ADR-0001/ADR-0002. Место хранения API-секрета решается параллельным тикетом [#4](https://github.com/menshov-anatoliy/transaction-journal/issues/4); дизайн зависит от него только через интерфейс чтения секрета.

## Goals / Non-Goals

**Goals:**

- Воспроизводимый конвейер «загрузка → сырые записи → домен», допускающий переразбор без обращения к бирже.
- Идемпотентность на биржевых идентификаторах на всех уровнях конвейера.
- Уважение лимитов и устойчивость к ошибкам сети/биржи при ручном режиме.
- Точность преобразования экспираций в закрывающие записи по ADR-0002, включая пропорциональное деление по конструкциям.

**Non-Goals:**

- Websocket-стримы и realtime — только REST по кнопке (решение карты).
- Фоновая синхронизация по расписанию (в тумане карты).
- Автопривязка сделок к конструкциям, метрики, UI полного экрана синка — отдельные capability.
- Funding-записи и конверсия валют — вне скоупа усилия.

## Decisions

### D1. Собственный тонкий REST-клиент вместо SDK

HttpClient + HMAC-SHA256 (hex lower) по официальному C#-примеру Bybit; строка запроса собирается вручную и побайтово совпадает в URL и подписи; `recv_window=5000`, timestamp из `DateTimeOffset.UtcNow`. Общепринятого официального C# SDK нет, а объём — четыре GET-эндпоинта. Клиент ограничен read-only эндпоинтами на уровне кода: методы только на чтение.

Альтернатива: сторонний bybit-SDK — отклонено из-за зависимостей и лишней поверхности.

### D2. Трёхслойный конвейер: загрузчик → сырые записи → производный домен

- **Загрузчик (Bybit gateway + sync engine)** знает эндпоинты, окна, курсоры, лимиты; пишет сырые записи пачками.
- **Сырое хранилище** (EF Core/SQLite): `RawExecution` (JSON записи исполнения, ключ `execId`), `RawDelivery` (JSON delivery-записи, ключ `symbol + deliveryTime`), `RawInstrument` (JSON спецификация), `SyncRun`/`SyncState` (режим, границы окон, водяной знак, счётчики, ошибки). Уникальные индексы по биржевым ключам дают идемпотентность вставки на уровне БД.
- **Материализатор** выводит доменные представления из сырых записей детерминированно; переразбор — локальная операция.

Альтернатива: сразу разбирать в домен при загрузке — отклонено: правила разбора будут уточняться (знак комиссий, деление delivery), а перечитывать биржу нельзя.

### D3. Закрывающие записи экспираций — производные, а не мутируемые строки

Закрывающие записи delivery/OTM вычисляются из `RawDelivery` + справочника `deliveryTime` + текущих привязок сделок при чтении (в согласии с решением гриллинга [#5]: всё производное пересчитывается). Сырые delivery-записи — единственный источник; пропорции деления по конструкциям пересчитываются при перепривязке сделок автоматически. Ручные пометки закрытия (fallback) останутся пользовательскими записями и в этот слой не входят.

Альтернатива: материализовать закрывающие записи строками таблицы — отклонено: перепривязка сделок потребовала бы синхронной правки и порождала рассинхрон.

### D4. Окна и курсоры

- Execution list: 7-дневные окна назад, `limit=100`, курсор `nextPageCursor`; категории `linear` и `option` — отдельными проходами. Сортировка desc: при инкременте проход останавливается, когда страница целиком состоит из известных `execId`.
- Delivery-record: 30-дневные окна, `limit=50`, дедуп `symbol + deliveryTime`; проход по `option` и `linear`.
- Инкрементальное окно: от водяного знака минус перекрытие (настраиваемый параметр, дефолт — сутки), защита от граничных гонок времени.
- OTM-детектор: после каждого прохода ищет инструменты с прошедшим `deliveryTime`, ненулевым остатком в домене и отсутствующей записью в `RawDelivery` — и выводит нулевое закрытие.

### D5. Resilience через Polly и заголовки лимитов

Фиксированный минимальный интервал между запросами (с запасом против 50 req/s), чтение `X-Bapi-Limit-Status`/`X-Bapi-Limit-Reset-Timestamp`, пауза при исчерпании. Ретраи Polly: экспоненциальный бэкофф на сеть/5xx (короткий), на `retCode 10006` — пауза секунды, на HTTP 403 «access too frequent» — длинная пауза (~10 минут) с ограниченным числом попыток и внятной ошибкой пользователю. Прогресс синка пишется в `SyncRun` поэтапно — прерванный запуск продолжается повторным нажатием без дублей (идемпотентность вставки + ранние стопы).

### D6. Секрет и конфигурация

Клиент получает ключ/секрет через интерфейс поставщика конфигурации; конкретное место хранения определит тикет [#4](https://github.com/menshov-anatoliy/transaction-journal/issues/4). Сверка часов с `GET /v5/market/time` перед подписью при ошибках `10003`-класса. Базовый URL (`api.bybit.com` / зеркало) — параметр конфигурации.

### D7. Материализация сделок

Сделка из записи исполнения: знаковое количество (`side`), `execPrice`, комиссия `execFee` со знаком и `feeCurrency` (USDC учитывается как USDT по ADR-0001), `isMaker`, `symbol` → справочник инструментов. Парсинг символа опциона `{BASE}-{dMMMyy}-{strike}-{C|P}` (InvariantCulture) сверяется с `RawInstrument`; канонические `optionsType`/`deliveryTime` берутся из справочника, а не из строки. Новые сделки всегда попадают во «Входящие».

## Risks / Trade-offs

- [Глубина execution list не задокументирована биржей] → backfill фиксирует достигнутую самую раннюю запись как границу; контроль полноты — сверка объёма с transaction-log (2 года) предупреждением, не блокирующим.
- [Знак `execFee` для rebate задокументирован косвенно] → при первом реальном синке проверить maker-сделки; правило разбора изолировано в материализаторе и правится без перезагрузки биржи.
- [IP-блок 403 на ~10 минут ломает UX ручной кнопки] → длинный бэкофф с индикацией статуса; для наших объёмов (сотни запросов на год истории) вероятность мала.
- [Производные закрывающие записи вычисляются при каждом чтении] → объёмы персонального журнала малы; при росте — кэш вычислений, не меняющий контракт.
- [Деление delivery по конструкциям зависит от привязок на момент просмотра] → это и есть требование ADR-0002 (пропорционально остаткам); производный пересчёт гарантирует согласованность после перепривязки.

## Migration Plan

Проект greenfield: схема сырого хранилища создаётся EF Core-миграцией в рамках задач change; отката данных нет. Откат кода не портит журнал — сырые записи остаются источником.
