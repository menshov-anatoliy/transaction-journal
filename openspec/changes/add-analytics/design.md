# Design

## Context

Стек и семантика зафиксированы: C#/.NET, EF Core + SQLite, локальный инструмент одного пользователя; сделка = одно исполнение, позиция — производный остаток, всё производное пересчитывается при чтении (CONTEXT.md, гриллинг [#5](https://github.com/menshov-anatoliy/transaction-journal/issues/5)). Change `add-bybit-sync` ([#8](https://github.com/menshov-anatoliy/transaction-journal/issues/8)) материализует сделки с комиссиями и закрывающие записи экспираций (ADR-0002); `add-core-domain` ([#9](https://github.com/menshov-anatoliy/transaction-journal/issues/9)) даёт конструкции с выделенным капиталом, привязки по `execId`, ручные пометки и корректировки, а его D3 объявляет кэш марок контрактом со слоем аналитики. Research-тикет [#2](https://github.com/menshov-anatoliy/transaction-journal/issues/2) подтвердил публичный эндпоинт тикеров для марок без аутентификации. MCP-контракт ([#7](https://github.com/menshov-anatoliy/transaction-journal/issues/7)) требует `unrealized_pnl` с `marks_as_of` и null при сбое марок.

## Goals / Non-Goals

**Goals:**

- Собственный расчёт реализованного PnL (FIFO с комиссиями), не зависящий от биржевых итогов.
- Оценка нереализованного PnL марками на момент запроса с предсказуемой деградацией при сбое.
- Провайдер марок как общая инфраструктура: оценка остатков и дефолт ручной пометки закрытия.
- Метрики позиции и конструкции: агрегаты, проценты от капитала, даты и длительность.
- Единый читающий слой для UI ([#12](https://github.com/menshov-anatoliy/transaction-journal/issues/12)) и MCP `get_analytics` ([#11](https://github.com/menshov-anatoliy/transaction-journal/issues/11)).

**Non-Goals:**

- Расширенные метрики (win-rate, грики, графики PnL, сравнение конструкций) — туман карты.
- Экспорт отчётов (CSV/Excel) — туман карты.
- Funding и конверсия валют — вне скоупа усилия; мультипользовательность и торговые операции — тем более.
- Журнал аудита и версионирование результатов — нет в MVP (решение [#5](https://github.com/menshov-anatoliy/transaction-journal/issues/5)).

## Decisions

### D1. Движок FIFO работает потоком записей, без хранимых результатов

Вход — единый хронологический поток записей позиции: сделки (количество, цена, комиссия) и закрывающие записи с эффективными ценами (delivery по внутренней стоимости, OTM по нулю, ручная пометка по цене пользователя — ADR-0002). Движок сопоставляет встречные части по FIFO, накапливает реализованный PnL и комиссии, возвращает непокрытый остаток и его среднюю цену (количество-взвешенная цена непокрытых слоёв) для нереализованной оценки и показа в метриках позиции; текущая марка открытой позиции берётся из кэша провайдера (D2) тем же запросом, что и оценка нереализованной части. Согласовано с `add-core-domain` D1 (единственный мутируемый агрегат) и `add-bybit-sync` D3 (производное пересчитывается): результат — функция текущих данных, сгенерить и сохранить его некому и незачем.

Альтернатива: материализованные итоги с обновлением при каждой правке — отклонена: порождает рассинхрон при свободных переносах сделок (тот же аргумент, что и в sync D3).

### D2. Провайдер марок — публичные тикеры с кэшем последней известной марки

Отдельный сервис: HTTP-запрос публичного эндпоинта тикеров (без API-ключа, без SDK — решение [#2](https://github.com/menshov-anatoliy/transaction-journal/issues/2)), кэш «инструмент → последняя марка + время получения». Обслуживает два потребителя: оценку нереализованного PnL при запросах метрик и дефолт цены ручной пометки закрытия (`add-core-domain` D3). Единственное новое хранилище change.

### D3. Сбой марок — деградация, а не ошибка

Недоступность тикеров не блокирует чтение метрик: `unrealized_pnl` и `marks_as_of` — null с признаком ошибки, реализованный PnL, комиссии, даты и проценты возвращаются как есть. Закрытые позиции марок не требуют вовсе. Контракт зафиксирован MCP-гриллингом [#7](https://github.com/menshov-anatoliy/transaction-journal/issues/7) — UI наследует ту же семантику.

### D4. Проценты и итог — чистые функции текущих данных

Итог конструкции = Σ (реализованный + нереализованный) позиций + внешние корректировки. Проценты считаются в читающем слое от текущего значения выделенного капитала (требование `domain/constructions` requirement-allocated-capital: правка капитала меняет только проценты). Отдельного хранимого «итога» нет — частный случай D1.

### D5. Даты и длительность — производные, статус им не противоречит

Позиция: открытие — время первой записи, закрытие — момент обнуления остатка. Конструкция: открытие — время первой сделки, закрытие — момент обнуления последней позиции; длительность открытой — до текущего момента. Ручной статус конструкции (решение [#5](https://github.com/menshov-anatoliy/transaction-journal/issues/5)) остаётся независимым ярлыком: «закрыта» руками при живом остатке не подменяет аналитического закрытия и наоборот.

### D6. Комиссии и валюты — из записей исполнения, USDC по паритету

Комиссия берётся из материализованной записи исполнения и входит в результат со знаком уменьшения; USDC-номиналы (премии, комиссии, delivery) — по паритету 1:1 (ADR-0001). Funding-записи не запрашиваются и в расчёт не попадают — граница проходит на входе движка, а не фильтром внутри.

## Risks / Trade-offs

- [Пересчёт при каждом чтении] → объёмы персонального журнала малы; при росте — прозрачный кэш вычислений, не меняющий контракт (тот же риск, что и в sync/domain).
- [Устаревшая марка в дефолте ручной пометки] → пользователь вправе задать цену явно; кэш штампуется временем, UI может показать возраст марки.
- [Расхождение с биржевыми итогами] → осознанное следствие собственного расчёта; сверка с `deliveryRpl` — предупреждение, не блокировка (ADR-0002).
- [Сдвиг дат при закрытии и переоткрытии позиции] → дата закрытия — последнее обнуление по текущему набору записей; при переоткрытии сдвигается при чтении (согласовано с D1).

## Migration Plan

Greenfield: единственная новая структура — кэш марок (инструмент, цена, время получения), создаётся EF Core-миграцией в задачах change. Порядок с `add-bybit-sync` и `add-core-domain` не связан: движок читает их таблицы, ничего не перемещая; данных нет, отката не требуется.
