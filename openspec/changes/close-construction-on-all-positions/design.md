# Design

## Context

Статус и период жизни конструкции вычисляет `ConstructionAssembler.UpdateDerivedState` по составу опционных ног; фьючерсные исполнения привязываются после обработки опционного таймлайна в `BindLinearExecutions` по периодам `[OpenedAtMs, ClosedAtMs]`. Отсюда круговая зависимость нового правила: период жизни нужен для привязки фьючерсов, а момент закрытия теперь зависит от фьючерсного остатка, который образуют привязанные фьючерсы. Seed инкрементной сборки (`AssemblySeedConstruction`) несёт только опционные ноги; фьючерсные остатки существующих конструкций берутся из `PositionReadModel` (агрегат привязанных сделок и закрывающих записей — включая ручные пометки).

## Goals / Non-Goals

**Goals:**

- Статус и `ClosedAtMs` определяются всеми позициями; затухающая конструкция продолжает принимать фьючерсы до обнуления остатка.
- Детерминизм сохраняется: повторная сборка над тем же сырьём даёт тот же план.
- Инкрементная и полная сборки сходятся к одинаковым статусам на одних данных (с учётом известного расхождения разрезанных роллов — ADR-0004).

**Non-Goals:**

- Изменение правил усреднения, роллов и кластеризации окон.
- Пересмотр привязки «перекрытие → более ранняя конструкция».
- Изменение статусирования ручных конструкций и «архива».

## Decisions

### D1. Хронологический однопроходный алгоритм привязки фьючерсов вместо итеративного фиксирования точки

После обработки опционного таймлайна активы получают фьючерсные исполнения в порядке времени. Для каждого актива поддерживается хронология конструкций: конструкция «покрывает» момент T, если `OpenedAtMs <= T` и она ещё не закрыта. Закрытие вычисляется на лету: конструкция закрывается в момент, когда одновременно обнулены прикрытие (известно из опционного таймлайна) и накопительный фьючерсный остаток (сумма привязанных фьючерсных исполнений с учётом seed'а). Сделка привязывается к первой (по `OpenedAtMs`, `Id`) из покрывающих. 

- Альтернатива «двухфазный пересчёт периодов до сходимости» отвергнута: неочевидная сходимость и риск недетерминизма; однопроходный хронологический проход даёт тот же результат без итераций.
- Момент закрытия — время события, обнулившего последнюю позицию: delivery/OTM-время для опционной ноги, время фьючерсного исполнения для фьючерса. Seed-остаток учитывается как начальное состояние.

### D2. Прогон хранит фьючерсные остатки конструкций

`ConstructionState` получает знаковый фьючерсный остаток (по одному на актив — конструкция одноактивна). Для seeded-конструкций он инициализируется из seed'а; `UpdateDerivedState` учитывает его наравне с ногами: `hasLivePosition = любая нога != 0 || futures != 0`.

- Роллы, усреднения и классификация закрывающих опционных сделок не читают фьючерсный остаток — правила опционной сборки не меняются.

### D3. Seed инкрементной сборки пополняется фьючерсными остатками

`AssemblySeedConstruction` получает фьючерсный остаток и время последнего события позиции (для непрерывности `ClosedAtMs`). Источник — тот же вызов `PositionReadModel`, которым строятся ноги: позиции категории linear constructions того же актива. Ручные пометки закрывшего фьючерс остатка входят в остаток read-модели автоматически.

### D4. Имена и повторные открытия — без изменений

Имя выводится из живых опционных ног (ADR-0005); фьючерсный остаток в имя не входит, при затухании сохраняется последнее производное имя. Повторное появление ненулевой позиции (опционной ноги роллом или фьючерсной сделкой в закрытую конструкцию — период покрывает момент сделки) возвращает «открыта».

## Risks / Trade-offs

- [«Пыль» фьючерса держит конструкцию открытой неограниченно долго] → осознанно: риск жив; инструмент трейдера — ручная пометка закрытия фьючерсной позиции или сделка робота.
- [Полный пересбор стирает ручные пометки, и затухающая конструкция снова открывается] → принятое следствие семантики пересбора (`scenario-rebuild-wipes-manual-data`); документируется в ADR-0006.
- [Фьючерсная сделка в закрытую конструкцию меняет статус на «открыта» без опционной ноги] → не нарушает инвариант опционной основы: опционная позиция существует с нулевым остатком. Поведение согласовано с «повторное появление ненулевой позиции возвращает открытость».

## Migration Plan

Миграция базы не требуется. Приёмка на живой базе — полным пересбором (выбор пользователя); текущая база ручных данных не содержит, потери исключены. Откат — возврат кода сборщика и повторный пересбор.
