# Design

## Context

База журнала — единственный SQLite-файл `App_Data/journal.db` в режиме WAL (ADR-0003), разворачивается миграциями при старте. Доменные сервисы живут по паттерну «singleton над собственными опциями контекста: короткоживущий контекст на вызов». Синхронизация запускается одной командой `IJournalSyncService.SyncAsync` с трёх экранов (Constructions, Settings, Sync), ошибки запуска проходят наружу и показываются экраном; строка `SyncRun` пишется самим сервисом. Полный пересбор `ConstructionAssemblyService.RebuildAsync` вычищает пять доменных таблиц одной транзакцией; подтверждение уже перечисляет потери. Удаление пустой конструкции уже имеет диалог подтверждения в `ConstructionDetail.razor`. Мотивация — в `proposal.md` (Why).

## Goals / Non-Goals

**Goals:**

- Одна механика копии для всех операций: консистентный снапшот работающей базы, ротация, единая точка ошибок.
- Обязательный бэкап пересбора гарантируется самой доменной операцией, а не вызывающим кодом.
- Опциональные бэкапы встраиваются с минимальными изменениями экранов и существующих контрактов.

**Non-Goals:**

- Восстановление из копии через интерфейс (копия — файл на диске, восстановление ручное).
- Бэкапы по расписанию или перед миграциями схемы при старте.
- Выгрузка копий в облако, шифрование, сжатие.

## Decisions

### D1. Снапшот — `VACUUM INTO`

Копия создаётся одним SQL-оператором `VACUUM INTO '<путь>'` через короткоживущий контекст. SQLite строит консистентный снапшот работающей базы с учётом WAL-данных, не блокируя параллельных читателей; целевой файл компактится и обязан не существовать. Путь подставляется экранированным литералом (одинарные кавычки удваиваются); коллизия имён в ту же секунду разрешается суффиксом-счётчиком.

Альтернативы: копирование файлов `journal.db` + `-wal` — гонка с пишущим приложением, риск неконсистентной копии; `SqliteConnection.BackupDatabase` — рабочий, но требует второй открытого соединения и не сжимает файл. `VACUUM INTO` покрывает всё одним оператором.

### D2. Каталог, именование и конфигурация

Копии пишутся в `App_Data/backups` как `journal-<yyyyMMdd-HHmmss>-<причина>.db`, где причина — `rebuild`, `sync` или `delete-construction`. Метка времени — локальная, для читаемости пользователем; порядок ротации определяется по времени файла (`LastWriteTimeUtc`), а не по имени. Конфигурация: `Backup:Directory` (по умолчанию `App_Data/backups`) и `Backup:RetentionLimit` (по умолчанию 15) — в стиле существующих секций `Sync:*`.

### D3. Сервис бэкапа с предупреждениями ротации

`IJournalBackupService.CreateBackupAsync(reason, ct)` возвращает имя созданной копии и предупреждения ротации. Реализация — singleton над собственными опциями контекста (домашний паттерн): создать каталог, выбрать свободное имя, выполнить `VACUUM INTO`, затем ротацию «лучшие усилия»: перечислить копии по возрастанию времени файла и удалить старейшие за лимитом; ошибки удаления собрать предупреждениями, а не исключениями — неудача ротации не отменяет созданную копию и защищаемую операцию.

### D4. Обязательный бэкап — внутри `RebuildAsync`

`IJournalBackupService` инжектится в `ConstructionAssemblyService`; `RebuildAsync` делает копию до чтения снимка сырья и открытия транзакции вычищения. Неудача копии — исключение наружу к экрану, данные нетронуты. Альтернатива — оркестрация «копия, затем пересбор» в `Settings.razor` — отклонена: инвариант «пересбор только после копии» обязан держать сам доменный сервис, иначе любой новый вызывающий обойдёт защиту. Тесты пересбора обновляются заглушкой бэкапа.

### D5. Переключатель бэкапа синхронизации — таблица `AppSetting`

Новая key/value-таблица `AppSetting` (ключ — PK), миграция применяется штатным `Migrate()` при старте. Ключ `backup-before-sync`: отсутствие строки трактуется как «включён» — значение по умолчанию не требует записи. Доступ — маленький singleton-стор `IBackupPolicyStore` над опциями контекста.

Альтернативы: `appsettings.json` — не рантаймовая настройка пользователя; JSON-файл в `App_Data` — второй магазин состояния вразрез с ADR-0003 «единственное хранилище — SQLite».

### D6. Бэкап синхронизации — декоратор `IJournalSyncService`

`BackupGuardedSyncService` оборачивает `JournalSyncService`: читает политику, при включённой делает копию с причиной `sync`; неудача копии — исключение наружу до запуска синхронизации (строка `SyncRun` не создаётся — запуск не начинался). Одна точка встраивания закрывает все три кнопки запуска; экраны продолжают зависеть от `IJournalSyncService`, их тесты со заглушками не меняются.

### D7. Бэкап удаления — флажок в существующем диалоге

Диалог удаления в `ConstructionDetail.razor` получает флажок «сделать резервную копию» (включён по умолчанию, состояние живёт в диалоге, не персистится). Подтверждение: копия с причиной `delete-construction`, при неудаче — отмена удаления с сообщением, затем штатный `DeleteAsync`. Оркестрация остаётся в экране: опциональная политика — решение вызывающего, `ConstructionService` не меняется (ср. с D4: там инвариант, здесь — опция).

## Risks / Trade-offs

- [Копия большой базы замедляет старт операции] → копия делается до операции, читатели не блокируются (WAL); лимит ротации защищает диск; каталог и лимит настраиваются.
- [Ротация может удалить старую нужную копию] → лимит настраивается; имя хранит причину и время; свежайшая копия никогда не удаляется.
- [Нет места на диске — операция блокируется] → осознанный выбор: включённый бэкап обязателен; ошибка показывается причиной незапущенной операции.
- [Декоратор меняет поведение всех кнопок синхронизации] → экраны зависят от интерфейса и тестируются заглушками; поведение декоратора покрывается собственными тестами.
- [Новая таблица `AppSetting`] → тривиальная миграция, применяется при старте; откат кода оставляет таблицу безвредной.

## Migration Plan

Развёртывание: обычный запуск приложения — `Migrate()` создаёт `AppSetting`, каталог копий создаётся лени при первом бэкапе. Откат: вернуть прежний код; файлы копий и таблица `AppSetting` остаются на диске и не мешают.
