# Design

## Context

Индикатор финрезультата сегодня состоит из шкалы с плановыми зонами (`resolveScale(plannedRisk, plannedProfit, total)`), насечки худшего исхода (`borderAt` из `worstCaseUsdt`) и маркера текущего результата (`markerAt`). Семантика переработана с владельцем (грилл-сессия 03.11.2026), мотивация — в `proposal.md`, модель — в ADR-0021 и глоссарии (термины «Маркер изменения результата», «Порог проявления маркера», «Область описания маркеров», «Маркер текущего результата»). Ключевой факт архитектуры: сводная «С учётом зафиксированного синтетикой» (`SyntheticAdjustedTotalUsdt = RealizedPnL + Σ локов`) уже существует в `ConstructionDetailReadModel`, фьючерсные сделки уже входят в FIFO-реализованный результат, а роллы уже классифицируются как атомарные окна в `ConstructionAssembler` (правила v5). Новых доменных сущностей не требуется.

## Goals / Non-Goals

**Goals:**
- История накопленного зафиксированного результата как производная величина журнала: без хранения, с пересчётом при изменении распознавания связок.
- Единая точка истины значения метки — существующая сводная плюс корректировки; никакой второй агрегации.
- Порог проявления 5% планового риска и сплошная нумерация по выведенным — вычисляются на сервере, UI рендерит как есть.
- Цепочка «макет → перенос → сверка» (ADR-0011): design.pen правится первым через MCP Pen, скриншот-сверка — критерий закрытия.

**Non-Goals:**
- Не меняем плавающий маркер текущего результата, заливку, золотую зону и плановые зоны шкалы.
- Не трогаем `realRiskUsdt`/`realRiskStatus` — бейджи «∞»/«?» и предупреждения остаются как есть.
- Не вводим пользовательские настройки порога и не храним «скрытые» метки где-либо.
- Не меняем модель связок синтетики и правила сборки — только потребляем их результаты.

## Decisions

### D1. Маркеры — вычислитель в application-слое, поверх существующих величин
Новый вычислитель маркеров строит хронологию событий конструкции: записи журнала, сгруппированные по правилу окон сборки (ролл — одно окно, одно событие), каждая фьючерсная сделка отдельно, изменения набора действующих связок, корректировки PnL, закрывающие записи. Значение в точке события = накопленный зафиксированный денежный результат на срезе журнала: `RealizedPnL + Σ локов действующих связок + корректировки − входная стоимость ещё открытых остатков` (решение владельца по конфликту формулы и литералов сценариев: премия открытия фиксируется сразу — покупка стреддла за 100 даёт первый маркер −100). Входная стоимость открытых остатков берётся из FIFO-слоёв того же среза; при закрытии всех остатков значение совпадает со сводной формулой. Отвергнуто: хранение меток в БД (расходится с журналом при спорах связок, нарушает принцип «аналитика вычисляется при чтении» — `requirement-analytics-computed-on-read`); вычисление на фронте (дублирует доменную логику, недоступно для контрактов списка).

### D2. Триггеры и точки событий
Опционные исполнения группируются переиспользованием окон `AssemblyWindow` (та же 60-минутная атомарность, что в сборке: окно = ролл/усреднение/открытие — один маркер). Фьючерсные сделки робота не группируются — по маркеру на сделку. Событие связки — изменение множества действующих связок (появление/спор/снятие/ручная). Порядок событий — по времени записи, при равенстве — по стабильному идентификатору записи. Отвергнуто: маркер на каждое исполнение (дробит двухногие открытия и роллы — нарушает атомарность окна, закреплённую в домене).

### D3. Порог и нумерация — в read-модели, не в UI
Фильтр «отличие от последней выведенной ≥ 5% планового риска» и перенумерация выполняются на сервере: контракты публикуют уже выведенные маркеры с финальными номерами. UI не знает про подавленные события. Отвергнуто: фильтрация на фронте (потребовала бы публиковать все события и дублировать порог в TS; рассинхрон с областью описания).

### D4. Контракты: карточка — список, список/превью — последний
Карточка конструкции публикует `resultMarkers[]` (номер, время события, тип события, изменение от предыдущей выведенной, накопленный итог); контракты списка и превью — только `lastResultMarker` (итог, время). `worstCaseUsdt` удаляется из всех DTO. Проект — монорепо с единым деплоем SPA и API, отдельной версионаризации контракта не делаем (прецедент: удаление «Визуальной подсказки» в `2026-10-10-fix-finresult-indicator-real-risk`).

### D5. Геометрия и отрисовка
`computeFinResultGeometry` расширяет охват шкалы точками маркеров (min/max по плану, текущему маркеру и всем меткам); ветка клипа `borderAt` удаляется. Бейджи маркеров рендерятся над полосой (номер + сумма), вертикальный разнос при коллизии — по аналогии с существующим разносом подписей; подпись маркера текущего результата остаётся под полосой. Средний/компактный виды рисуют только последний маркер без номера и сумм — геометрия 132px компактного вида не меняется. Область описания — новый блок под полным индикатором в карточке (список + скролл, пустое состояние).

### D6. Сначала design.pen, потом код (ADR-0011)
Первая задача UI-блока — правка `design.pen` строго через MCP Pen: бейджи над полосой, область описания в обоих состояниях (заполненном и пустом), последний маркер в превью и компактном виде, обновлённый текст попапа «Как читать индикатор» (без насечки, по ADR-0021). Приёмка переноса — токенно-компонентное соответствие + обязательная скриншот-сверка живой карточки с макетом.

### D7. Удаление худшего исхода
`RealRiskCalculator` прекращает публикацию худшего платежа как отдельной метрики; из `ConstructionMetrics`, `ConstructionListRows`, `ConstructionsEndpoints`, `ConstructionCardEndpoints`, `RealRiskContract` поле `worstCaseUsdt` убирается. `realRiskUsdt`/`realRiskStatus` не меняются. Аудит прочих упоминаний `worstCase` (контекст чатов, подсказки, тесты) выполняется grep-задачей в `tasks.md`; ADR-0015 уже помечен заменённым.

## Risks / Trade-offs

- [Спор связки задним числом меняет историю меток] → метки полностью производные: пересчёт даёт согласованный результат, тест на сценарий `scenario-link-dispute-recomputes-history`; в попапе это не объясняется — поведение натуральное.
- [Вычисление истории на каждый запрос] → полный список считается только в карточке конструкции; список/превью получают лишь последний маркер; FIFO-движок и метрики уже вычисляются при чтении, стоимость шага истории — переиспользование тех же записей.
- [Плотность бейджей при длинной истории] → порог 5% планового риска, вертикальный разнос, область описания со скроллом; в компактных видах — один маркер.
- [Breaking-контракт `worstCaseUsdt`] → монорепо и единый деплой: фронт перестаёт читать поле в том же change; откат — revert всего изменения.
- [Расхождение последней метки и маркера текущего результата путает] → намеренно: метка — зафиксированный итог, маркер — «заберу сейчас»; сценарий `scenario-result-marker-last-vs-current` и текст попапа закрепляют различие.

## Migration Plan

Миграция данных не нужна: маркеры вычисляемые, хранимых артефактов нет. Развёртывание — обычное: удалить `worstCaseUsdt` из контрактов и UI в одном изменении. Откат — revert коммитов изменения; после отката насечка и метрика возвращаются без восстановления данных.
