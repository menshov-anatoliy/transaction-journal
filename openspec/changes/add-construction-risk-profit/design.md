# Design

## Context

Выделенный капитал сегодня — обязательное `decimal`-поле `Construction.AllocatedCapitalUsdt`; проценты результата обнуляются при нулевом капитале (правило «нулевой капитал не образует базы процентов» в `ConstructionMetricsCalculator`). Создание конструкции возможно только из «Входящих» (`Inbox.razor` → `IConstructionService.CreateAsync`), правка капитала — из деталей (`ConstructionDetail.razor` → `UpdateAllocatedCapitalAsync`). Проценты позиций от капитала считаются в `ConstructionDetailReadModel`. Панель журнала использует только абсолютный итог и капитала не касается. Риск и профит в системе отсутствуют. Активный параллельный change `add-mcp-server` строит MCP-контракт поверх тех же сервисов.

## Goals / Non-Goals

**Goals:**

- Капитал становится nullable с сохранением существующих значений и единым правилом «незаданный или нулевой капитал не образует процентов».
- Риск и профит хранятся как пара «значение + единица первоисточника» с свободной правкой и очисткой.
- Незаполненная единица вычисляется чистой функцией от текущего капитала при чтении; в БД не сохраняется.
- Подсказка «риск — итог — профит» в строке списка и сводке деталей строится презентационным слоем из готовых величин.

**Non-Goals:**

- Не вводим историю изменений и аудит риск/профит/капитала (как и у капитала сегодня).
- Не считаем риск автоматически из состава позиций — параметр либо введён, либо отсутствует.
- Не задаём риск/профит при создании конструкции (по запросу — только правкой существующей).
- Не трогаем MCP-контракт: он в параллельном change и синхронизируется там после этого.

## Decisions

### D1. Капитал — nullable-колонка, а не «нулевое значение»

`AllocatedCapitalUsdt: decimal → decimal?`; миграция EF делает колонку nullable, существующие значения сохраняются как есть. Пустое поле формы маппится в `null`.

Альтернатива — договориться, что 0 означает «не задан»: отвергнута, потому что 0 уже сегодня легитимное значение с явным правилом поведения (проценты null), а перегрузка смысла сломала бы различие «нет данных» и «задан ноль».

### D2. Риск и профит — четыре nullable-колонки: значение + единица первоисточника

`RiskValue decimal?`, `RiskUnit tinyint?` (enum `TargetUnit { Percent, Usdt }`), `ProfitValue decimal?`, `ProfitUnit tinyint?`. Инвариант: пара либо оба `null` (параметр отсутствует), либо оба заданы; `ConstructionService` отклоняет неполную пару `ArgumentException`. Значение вводится положительным числом: риск — допустимый убыток, профит — целевая прибыль; знак минус подсказка добавляет сама.

Альтернативы: две колонки `RiskPercent`/`RiskUsdt` с инвариантом «ровно одна заполнена» — вводит в заблуждение (вторая колонка никогда не хранит вычисленное); хранение вычисленной пары — отвергнуто: нарушает принцип «аналитика вычисляется при чтении и не хранится».

### D3. Контракт сервиса: два явных метода правки, null-параметры очищают

- `CreateAsync(string name, decimal? allocatedCapitalUsdt, string? comment)` — прежняя семантика, капитал опционален.
- `UpdateAllocatedCapitalAsync(long id, decimal? allocatedCapitalUsdt)` — `null` убирает значение.
- `UpdateRiskAsync(long id, decimal? value, TargetUnit? unit)` и `UpdateProfitAsync(...)` — оба аргумента заданы → установить; оба `null` → очистить; один задан → `ArgumentException`.

Альтернатива — один метод `UpdateTargetsAsync(...)` с DTO: отвергнута, лишний тип без выигрыша в читаемости; два симметричных метода повторяют стиль существующего интерфейса (`RenameAsync`, `UpdateAllocatedCapitalAsync`).

### D4. Конвертация единиц — чистая функция в Analytics, read-модели собирают величины

Отдельный статический вычислитель (например, `ConstructionTargetConverter`) без хранилища: `(value, unit, capital) → (percent?, usdt?)`. Правила: `Percent → Usdt = value / 100 * capital`; `Usdt → Percent = value / capital * 100`; капитал `null` или `0` → вычисляемая единица остаётся `null`. Read-модели списка и деталей (`ConstructionListReadModel`, `ConstructionDetailReadModel`) добавляют в DTO риск/профит обеими единицами.

`ConstructionMetrics` не расширяется: метрики строятся из позиций и корректировок, а риск/профит — атрибуты конструкции; смешение усложнило бы калькулятор. Подсказка — не метрика, а представление величин, поэтому проценты заполнения шкалы считает razor-слой.

### D5. Проценты — одно правило на всех уровнях

`ConstructionMetricsCalculator.Calculate` принимает `decimal? allocatedCapitalUsdt`; функция `Percent` возвращает `null` при `null` или `0` капитала. Read-модели позиций используют то же условие. UI показывает прочерк в сводке списка/деталей и опускает скобки с процентом в строках позиций (не выводит «(—)» рядом с абсолютной величиной).

### D6. Подсказка — шкала в USDT с нормировкой на доступные границы

Разметка: блок из подписи и полосы; полоса делится на зону риска (от левой границы до нуля) и зону профита (от нуля до правой границы), заполнение рисуется от нуля до текущего `TotalPnL`. Правила построения:

- Шкала строится в USDT: нормировка `|риск USDT| + |профит USDT|`; граница без USDT-величины (параметр в % при незаданном/нулевом капитале) на шкале не показывается.
- Граница без параметра убирает свою сторону; обе стороны без USDT-величин — полоса не выводится, подписи параметров не выводятся.
- Итог за границей: сторона заполнена до конца с классом-признаком пробоя (цвет), без изменения пропорций.
- `TotalPnL == null` (сбой марок): полоса заменяется признаком сбоя, как в колонках нереализованного PnL.
- Подписи границ выводят обе доступные единицы: «5% / 150».

В списке подсказка компактная (тонкая полоса в ячейке «Итог» или соседней ячейке строк), в деталях — полоса с подписями в сводке. Выбор места в разметке — за реализацией, поведение фиксировано спекой `ui/screens`.

### D7. Формы правки в деталях повторяют паттерн «действие → форма»

Панель действий деталей пополняется командами «Риск…» и «Профит…». Форма каждого параметра: два поля ввода («%» и «USDT»), заполняется ровно одно; при заданном капитале вторая единица показывается вычисленным значением (доступно только для чтения) сразу при вводе. Кнопки: «Сохранить», «Убрать» (очистка параметра; скрыта, если параметр не задан), «Отмена». Незаполненные оба поля при сохранении равносильны «Убрать». Валидация: положительное число в ровно одном поле; заполнение обоих — ошибка «введите значение только в одной единице».

Форма капитала: подпись «Выделенный капитал, USDT» (с заглавной — и в форме создания «Входящих»), пустое поле при сохранении убирает капитал; под полем — пояснение «пусто — капитал не задан».

## Risks / Trade-offs

- [Сломанные вызовы `CreateAsync`/`Calculate` при смене сигнатур] → Компилятор C# найдёт все места; обновить вызовы и тесты в том же шаге задач.
- [Параллельный change `add-mcp-server` строит контракт на старой сигнатуре] → Синхронизировать после применения этого change; зафиксировать в tasks финальный шаг проверки.
- [SQLite-миграция nullable-колонки] → EF Core SQLite переписывает таблицу; миграция без данных (копия схемы), откат — обратная миграция с дефолтом 0 для уже удалённого капитала.
- [Риск в % при незаданном капитале не образует шкалы] → Осознанный компромисс D6: параметры остаются видимы в форме правки и подписи, полоса просто не строится; правило зафиксировано и тестируется.

## Migration Plan

1. EF-миграция: `AllocatedCapitalUsdt` → nullable; добавить `RiskValue`, `RiskUnit`, `ProfitValue`, `ProfitUnit` (все nullable). Существующие строки не меняют значений.
2. Код и миграция применяются одним выпуском; развёртывания без данных между ними не требуется.
3. Откат: обратная миграция возвращает NOT NULL капитала (NULL → 0) и удаляет колонки риск/профит.
