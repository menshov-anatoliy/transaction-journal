# Design

## Context

Стек зафиксирован картой ([#1](https://github.com/menshov-anatoliy/transaction-journal/issues/1)): Blazor Server, локальный инструмент одного пользователя, язык интерфейса — русский. Облик — вариант A «Терминал» прототипа ([#6](https://github.com/menshov-anatoliy/transaction-journal/issues/6)): тёмная тема, верхняя навигация, плотные таблицы; правки гриллинга: корректировка PnL живёт внутри деталей конструкции, «Выбрать всё» во «Входящих», транзитная именованная вкладка конструкции. Доменные операции — контракты `add-core-domain` ([#9](https://github.com/menshov-anatoliy/transaction-journal/issues/9)); метрики и отметка марок — `add-analytics` ([#10](https://github.com/menshov-anatoliy/transaction-journal/issues/10)); команда синхронизации — `add-bybit-sync` ([#8](https://github.com/menshov-anatoliy/transaction-journal/issues/8)).

## Goals / Non-Goals

**Goals:**

- Пять экранов MVP, закрывающих все мутации домена: привязки, переносы, пометки, корректировки, комментарии, капитал, статусы.
- UI — тонкий слой: каждый экран читает read-модели и метрики, каждую мутацию выполняет через use-case сервисы домена; собственных доменных правил UI не вводит.
- Отсутствие данных отражается явно: сбой марок, пустые таблицы, недоступность синхронизации — видимые состояния, а не пустой экран.

**Non-Goals:**

- Автоподсказки привязки сделок, расширенные метрики, графики, экспорт — туман карты, вне MVP.
- Мобильная адаптация, аутентификация, мультипользовательность — вне скоупа усилия.
- Новые доменные правила и расчёты — принадлежат слоям `add-core-domain` и `add-analytics`.

## Decisions

### D1. Каркас «Терминал»: статические вкладки плюс транзитная вкладка конструкции

Верхняя панель показывает бренд, текущий экран и итог по журналу — всегда видимый ориентир. Статические вкладки: «Конструкции», «Входящие» (бейдж — число непривязанных сделок), «Настройки». Открытая в деталях конструкция получает именованную транзитную вкладку на фиксированном месте сразу после «Конструкций»: со статусной точкой и закрывается крестиком с возвратом к списку; при уходе на другой экран вкладка не закрывается, закрывается только крестиком или сменой конструкции. Отдельной вкладки «Корректировка PnL» нет — правка прототипа ([#6](https://github.com/menshov-anatoliy/transaction-journal/issues/6)).

### D2. Отдельного экрана корректировок нет — форма и таблица в деталях конструкции

Корректировка всегда принадлежит конструкции, поэтому форма добавления (дата, источник «робот/ручная», знаковая сумма, описание) и таблица существующих с inline-правкой и удалением живут в деталях конструкции. Это решение прототипа; таблица «все корректировки журнала» в MVP не строится.

### D3. Единственная команда синхронизации; режим выбирает система и показывается в журнале

Прототип показывал селект режима на «Настройках», но спека `sync/bybit-history` фиксирует единственную ручную команду «Синхронизировать» с автоматическим выбором режима (backfill при первом запуске, инкремент далее). UI следует спеке: кнопка «Синхронизировать сейчас» на «Настройках» и в тулбаре списка, применённый режим виден строкой журнала синхронизаций. Селект режима из прототипа не реализуется.

### D4. Сбой марок — видимое состояние нереализованных величин

По контракту `analytics/performance` нереализованный PnL и отметка времени марок возвращаются null при недоступности тикеров. Экраны показывают на месте нереализованных величин признак сбоя марок; реализованные метрики, комиссии и проценты остаются видимыми. Итог по журналу в этом случае помечается как неполный.

### D5. Inline-редактирование по месту в таблицах

Комментарии сделок и позиций, корректировки и статусы правятся в таблицах деталей без отдельных страниц; комментарий конструкции — в шапке деталей. Выбор строк «Входящих» и массовые действия — чекбоксы в таблице. Формы простых сущностей (создание конструкции, корректировка, ручная пометка) — модальные или встроенные формы над таблицей.

### D6. Ручная пометка закрытия — действие строки позиции

Позиция производная и не редактируется напрямую, поэтому единственное действие над строкой позиции (кроме комментария) — «закрыть пометкой»: диалог с ценой (по умолчанию — последняя известная марка из кэша провайдера) и временем. Поставленная пометка показывается в закрывающих записях конструкции, где её можно править и удалить; избыточная закрывающая запись отражается предупреждением (контракт `add-core-domain`).

### D7. Состояние экранов — стандартный контур Blazor Server

Выбор «Входящих», открытая вкладка конструкции и состояние форм живут в circuit-состоянии компонентов; персистентности не требуется. Данные перечитываются из read-моделей при каждом открытии экрана — устаревших значений UI не показывает (контракт «аналитика при чтении»).

## Risks / Trade-offs

- [Отступление от прототипа: нет селекта режима синка] → осознанное следование спеке `sync/bybit-history`; режим виден в журнале синхронизаций (D3).
- [Плотные таблицы без пагинации] → объёмы персонального журнала малы; пагинация добавится правкой без смены контракта экранов.
- [Потеря выбора «Входящих» при обрыве circuit] → выбор транзитен, данные не теряются; повторный выбор дешев.
- [Модальные формы в Blazor Server] → простейшие встроенные диалоги без JS-зависимостей; при усложнении заменяются компонентом без смены требований.

## Migration Plan

Greenfield: экраны создаются задачами change поверх сервисов `add-core-domain`; данных и существующего UI нет, отката не требуется. Порядок с `add-analytics` и `add-bybit-sync` не связан: UI потребляет их контракты чтения и команды как есть.
