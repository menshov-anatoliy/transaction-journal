# Design

## Context

Корпус v1 в `rules/` (34 карточки, 11 машинных ключей, схема и fail-fast валидность — [ADR-0007](../../../docs/adr/0007-hints-agent-architecture.md), [#26](https://github.com/menshov-anatoliy/transaction-journal/issues/26), [#28](https://github.com/menshov-anatoliy/transaction-journal/issues/28)); структура решения готова предыдущим change `restructure-ddd-solution` ([ADR-0008](../../../docs/adr/0008-ddd-solution-structure.md)); доменная модель подсказки и UI зафиксированы [#30](https://github.com/menshov-anatoliy/transaction-journal/issues/30), критерии готовности — [#31](https://github.com/menshov-anatoliy/transaction-journal/issues/31). Исполнение всегда вручную: подсказки — только рекомендации; Telegram и LLM-изложение — следующий change, здесь deliveries нет.

## Goals / Non-Goals

**Goals:**

- Проект `TransactionJournal.Hints`: снимок корпуса за проход, 11 машинных триггеров, дедуп «правило × субъект × окно», хранение подсказок историей в SQLite, UI-панель с «Применено»/«Отклонено» и ручной запуск.
- Фикстурные e2e: каждый ключ корпуса v1 парами «сработало / не сработало»; дедуп-окно; fail-fast корпуса; панель показывает факты триггера ([#31](https://github.com/menshov-anatoliy/transaction-journal/issues/31)).

**Non-Goals:**

- Доставка сводки (Telegram, расписание, LLM-изложение, буферизация) — change `add-summary-channels`.
- Пополнение корпуса: срезы v2 (ОК, Жупин, ИК-БТ), подсказки входа v2 (порог AC-13, канал ввода вью), политика конфликтов источников ([#36](https://github.com/menshov-anatoliy/transaction-journal/issues/36)).
- Инструкции агента `agent-prompt.md` и `IChatClient` — вводятся следующим change вместе с изложением.
- `--hints-once` CLI, R3-сессия, метрики качества, MCP-сервер ADR-0003.
- Синхронизация журнала агентом: проход только читает журнал ([#21](https://github.com/menshov-anatoliy/transaction-journal/issues/21)).

## Decisions

### D1. Проект Hints — окружение с портами; адаптеры в Infrastructure

`src/TransactionJournal.Hints` ссылается только на `TransactionJournal.Domain` ([ADR-0007](../../../docs/adr/0007-hints-agent-architecture.md), [ADR-0008](../../../docs/adr/0008-ddd-solution-structure.md)). Свои потребности движок выражает портами, объявленными в Hints: `IJournalSnapshotReader` (журнал-данные для триггеров), `IMarkSource` (рыночные марки), `IHintStore` (запись и чтение подсказок), `IClock`. Реализации — адаптеры в `TransactionJournal.Infrastructure` (EF поверх той же SQLite, Bybit-клиент) по образцу store-портов Domain: Infrastructure ссылается на Hints так же, как на Domain и Application, — направление «адаптер → порт» сохраняется. Регистрация — composition root Web. Домен не узнаёт о подсказках: ни один тип Domain не ссылается на Hints.

### D2. Снимок корпуса и валидация — одно чтение, одна агрегированная ошибка

Загрузчик читает каталог (путь — настройка, дефолт `rules/` рядом с exe), парсит YAML всех карточек и проверяет схему (поля `id`, `title`, `character`, `clarity`, `scope`, `status`, `thresholds`, `trigger.implementation`, `action.hintTemplate`, `sources`; `id` = имя файла). Все проблемы собираются за один проход и поднимаются одной агрегированной ошибкой `CorpusInvalidException` до построения снимка и любых чтений журнала/рынка; хост живёт, ошибка видна в логе прохода и UI ручного запуска ([#28](https://github.com/menshov-anatoliy/transaction-journal/issues/28)). Неизвестный ключ `trigger.implementation` схеме соответствует — это не битость: карточка уходит в чек-лист и лог «непокрытых кодом». Снимок неизменяем на время прохода; `retired`-карточки входят в снимок только для гашения живых записей.

### D3. Триггеры — чистые функции по ключам; корпус данных не содержит логики

Триггер — чистая функция `(журнал-снапшот, марки, карточка) → факты | нет срабатывания`, выбираемая по `trigger.implementation`. Реализуются 11 ключей v1; числовые пороги движок берёт из `thresholds` карточки, а не из кода. Вычисления журнала переиспользуют движки Domain (FIFO, сборка конструкций, цели Risk/Profit сущности Construction). Формулировка текста — рендер `hintTemplate` фактами; чёткость задаёт императив/«[решение]». LLM в этом контуре нет — «никаких прогнозов» выполняется структурно.

### D4. Хранение подсказок — та же SQLite, история целиком

`IHintStore` реализован в Infrastructure таблицами подсказок в существующей SQLite-базе (EF, миграция Infrastructure): запись самоописательна, без внешних ключей в доменные таблицы, кроме идентификатора субъекта-конструкции как значения. Статусы `new/applied/dismissed/expired` + `firstSeenAt`; терминальные записи не удаляются. Read-модель подсказок (панель, журнал, индикаторы) живёт в Hints как интерфейс поверх `IHintStore`; компоненты Web получают её через DI — Web ссылается на Hints как внешний слой, Application и Domain о подсказках не знают.

### D5. Дедуп-окно по ключу «правило × субъект (+ период)»

Окно представлено самими записями: текущее окно правила и субъекта — запись со статусом `new/applied/dismissed` (не `expired`). Перед созданием подсказки движок спрашивает `IHintStore` о записи текущего окна этого ключа: есть — новая подавлена (включая `dismissed` — отклонённое не повторяется). Условие на проходе не выполняется, а живая запись есть — гасится в `expired`. Для периодных правил (периодные лимиты ac-01) в ключ окна входит вычисленный период (неделя/месяц/квартал из фактов) — смена периода = новое окно = новая подсказка. Закрытие субъекта: первый проход после закрытия гасит живые записи; вывод правила: при загрузке снимка гасятся живые записи retired/удалённых ключей — журнал в обоих случаях не участвует.

### D6. UI — панель, индикатор, журнал, кнопка запуска

Индикатор числа живых подсказок в строке конструкции; панель «Подсказки» в деталях (живые сверху по группам справочника v1, терминальная история свёрнута); та же панель на обзорном экране для субъекта «журнал»; общий read-only журнал с фильтрами статуса/характера/группы; кнопки «Применено»/«Отклонено» — единственные мутации; кнопка ручного запуска прохода (успех — обновление панелей; ошибка корпуса — агрегированный список проблем). Компоненты живут в Web, данные получают через read-модель Hints.

## Risks / Trade-offs

- [Инфраструктурная деталь: ручной запуск из UI требует фонового выполнения без блокировки контекста Blazor] → Запуск как Task с индикатором занятости; тот же код, что и плановый проход следующего change.
- [Смещение порогов корпуса и движка (данные ушли вперёд кода)] → Пороги только в `thresholds` карточек; e2e фиксируют пары «сработало/не сработало» на фикстурах, рассинхрон виден сразу.
- [Рост числа триггеров в v2 потребует расширения набора] → Реестр ключей — явный словарь в коде; новый ключ = новая чистая функция + пара фикстур, корпус не меняет код сам.
- [Подсказки в той же SQLite — конкуренция записей с UI] → WAL (ADR-0003) и короткие транзакции записи; объём записей мал (десятки в день).

## Migration Plan

Новый проект и таблицы добавляются к готовой DDD-структуре; данных подсказок ещё нет — миграция хранилища без переносов. Откат — удаление проекта Hints и таблиц; на домен и журнал не влияет.
