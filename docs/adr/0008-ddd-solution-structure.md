# Целевая структура решения — DDD-слои пятью проектами, миграция без изменения поведения

Журнал вырос из папочных слоёв одного проекта (`src/TransactionJournal` с подпапками Domain/Data/Sync/Materialization/Analytics/Bybit/Components/Ops): граница между слоями держится только дисциплиной, компилятор её не проверяет, и перед построением агента подсказок ([ADR-0007](0007-hints-agent-architecture.md)) связность стала бы расти быстрее, чем её сдерживает ревью. Решено перестроить решение в пять проектов с DDD-слоями: `TransactionJournal.Domain` (POCO-сущности без EF, чистые движки и парсеры, store-порты домена), `TransactionJournal.Application` (use-case-сервисы и read-модели с доступом к хранилищу, оркестрация Materialization/Sync/Analytics, внешние шлюзы-порты, read-only контракт чтения для MCP и R3), `TransactionJournal.Infrastructure` (EF Core с JournalDbContext, fluent-конфигурацией и миграциями, Bybit-клиент, Ops), `TransactionJournal` (Blazor-компоненты и Program.cs — composition root) и `TransactionJournal.Hints` (окружение агента по ADR-0007, строится после миграции). Принцип раскладки: чистая логика без I/O — Domain; оркестрация с хранилищем — Application; адаптеры и клиенты — Infrastructure; UI — Web. [ADR-0003](0003-stack-single-exe-dotnet-sqlite.md) подтверждён без изменений: имя exe, App_Data и режим `--mcp` того же исполняемого файла сохраняются; read-only контракт — порты в Application, реализация чтения — Infrastructure. Namespace приводятся к проектам (root namespace = проект, подпространства сохраняются, например `TransactionJournal.Application.Sync`); тесты остаются одним проектом `tests/TransactionJournal.Tests` с папками, зеркалящими проекты. Решение принято на карте [#19](https://github.com/menshov-anatoliy/transaction-journal/issues/19) (тикет [#29](https://github.com/menshov-anatoliy/transaction-journal/issues/29)); миграция — серия PR Domain → Infrastructure → Application → Web с зелёными тестами после каждого шага, порядок фиксирован в тикете [#31](https://github.com/menshov-anatoliy/transaction-journal/issues/31).

## Considered Options

- Статус-кво — папочные слои без проектов: отклонён. Граница не enforced компиляцией: зависимость любого слоя на любой пакет проходит незаметно для ревью, а движок подсказок и read-only контракты MCP/R3 требуют явных порт-границ.
- Немедленная миграция одним большим PR: отклонена. Слишком широкий фронт для сохранения «тесты зелёные без правки ассертов»; поэтапная серия шагов даёт контрольную точку после каждого слоя.
- Перестройка сразу вместе с агентом подсказок (интерлив): отклонён (тикет [#31](https://github.com/menshov-anatoliy/transaction-journal/issues/31)). Два незакрытых фронта посреди миграции; движок строится после неё сразу на целевой структуре, без перекладки готового кода Hints.
- Вертикальные срезы вместо слоёв: не рассматривались всерьёз — кодовая база одного пользователя уже организована вокруг слоёв, срезы потребовали бы переписывания, а не переноса.

## Consequences

- Зависимости направлены внутрь: Web → Application → Domain; Infrastructure реализует порты Application и Domain; Hints зависит только от Domain. Нарушение становится ошибкой компиляции, а не замечанием ревью.
- Перенос кода механичен (пространства имён, csproj, solution), но широк: каждый шаг миграции закрывается полной сборкой решения и зелёными тестами без правки ассертов — только переносы и namespace.
- EF-конфигурация уезжает от сущностей в Infrastructure целиком: Domain остаётся POCO, migrations остаются в одном проекте; цена — дисциплина «не тянуть EF-типы в Domain».
- Имя exe, App_Data, режим `--mcp` и поведение приложения не изменяются: реструктуризация не является функциональным изменением; любые находки поведения по ходу миграции фиксируются отдельными change, а не правками внутри шагов.
