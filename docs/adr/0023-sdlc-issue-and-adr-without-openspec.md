# Агентский цикл разработки без OpenSpec: спецификация в GitHub Issue, долговечные решения — в ADR

Новые доработки проходят агентский цикл, где каноническая спецификация живёт в GitHub Issues — бриф агента комментарием к issue либо отдельный issue-спека со срезами в sub-issues (скиллы `triage` → `to-spec` → `to-tickets` → `implement`), а трудно обратимые решения фиксируются ADR в `docs/adr/`; OpenSpec change для новой работы не создаются. Причина — единый носитель для спецификации, обсуждения, состояния и истории без дублирования «issue ↔ change» и без церемонии proposal/design/specs/tasks/sync/archive на каждую доработку. Живой спецификацией текущего поведения становятся тесты с traceability-метками на `issue:#N` и `adr:`; `issue:#N` перестаёт быть временной ссылкой.

## Considered Options

- Всегда OpenSpec change — отклонено: живая спецификация `openspec/specs` и стабильные `Traceability ID` ценны, но спецификация дублировалась бы в issue и change, а церемония непропорциональна мелким доработкам.
- Выбор между OpenSpec и issue по размеру доработки — отклонено: два конвейера без жёсткого правила выбора — источник расхождений и ручных решений на каждой задаче.

## Consequences

- `openspec/specs` и существующие метки `openspec:` замораживаются как legacy без массовой переписки; при смысловой правке блока метка переводится на `issue:#N`/`adr:`.
- Активные changes доводятся по старому конвейеру; `openspec-apply-all` ([ADR-0012](0012-openspec-apply-all-sequential-execution.md)) не используется для новой работы.
- `.github/instructions/traceability.instructions.md` требует приведения к новой модели целей отдельной правкой.
- Ответ на вопрос «что система делает сейчас» восстанавливается из тестов и кода, а не из сводного документа спецификаций.
