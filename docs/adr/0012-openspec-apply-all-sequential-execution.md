# openspec-apply-all — последовательное исполнение: тонкий оркестратор, блочные исполнители на openspec-apply-change, один integration-worktree

Скилл `.agents/skills/openspec-apply-all` исполнял OpenSpec change параллельно: worker-worktree и ветка на каждый пункт, планировщик слотов с лимитом 3, squash-интеграция отдельным интегратором, тяжёлый `run.json`. Аудит прогона `add-agent-chat` (2026-10-09) показал: ни один зафиксированный факт не подтверждает выгоду параллельности, а её накладные расходы подтверждены — преждевременный worktree из-за ошибки графа пересечений, ручной `run.json` с микрообновлениями и потерянными статусами, тройной полный baseline с потерянной диагностикой, многословные промпты и отчёты, обход safeguards (`--no-verify`, `git branch -D`). Решение: последовательная модель в едином integration-worktree — **оркестратор** (план, состояние, влитие, приёмка; контекст не засоряется кодом) запускает по одному синхронному **блочному исполнителю** — суб-агенту, который вызывает скилл `openspec-apply-change` с жёстким охватом пунктов **когерентного блока** (по умолчанию один пункт `tasks.md`; укрупнение — только явной группировкой пользователя либо его согласием на предложение оркестратора), сам отмечает выполненные пункты и коммитит во временную блочную ветку; оркестратор компактно проверяет и вливает блок одним squash-коммитом. Свежий контекст на каждый блок закрывает главную цену чисто последовательной альтернативы — накопление контекста в одном длинном окне.

## Considered Options

- Текущий параллельный контракт с `workerLimit=1` — отклонён: оставляет весь интеграционный overhead (worker-worktree, слоты, squash-церемонии, тяжёлое состояние) без единого подтверждённого выигрыша.
- Последовательное исполнение с opt-in параллельностью для независимых задач — отклонено: удерживает планировщик слотов и граф пересечений кода — подтверждённый источник расходов и ошибок планирования.
- Один ведущий агент реализует всё сам (первичный кандидат handoff) — отклонён: длинная сессия накапливает контекст в одном окне; блочные исполнители дают свежий контекст каждому блоку при той же последовательности.
- Схема `implement-spec` (per-ticket ветки + merger-субагенты + «фронтир» максимальной конкурентности) — отклонена: тот же параллельный контракт в мягкой форме, без изоляции каталога пользователя, run-состояния и гарантий возврата.

## Fixed Mechanics

- **Роли**: оркестратор — единственный владелец состояния и integration-ветки; блочный исполнитель — суб-агент одного блока. Суб-агенты только триёх видов: блочные исполнители (строго синхронно), крупное независимое исследование (заметки вне репо), итоговое `code-review`; параллельная реализация и вложенные исполнители запрещены.
- **Блок**: по умолчанию один пункт `tasks.md`; оркестратор вправе предложить объединение связанных пунктов (пункт потребляет контракт/результат соседнего) одним вопросом на планировании, решение всегда за пользователем; номера пунктов сохраняются в `Task:`-строках коммита, неполные требования не отмечаются.
- **Исполнитель**: вызывает `openspec-apply-change` в integration-worktree с охватом «только пункты блока» (нативный скилл иначе loops по всем pending); паузы скилла («спроси пользователя») транслирует в блокер оркестратору; отметки `- [ ]` → `- [x]` делает сам (нативное поведение); коммитит реализацию с отметками во временную блочную ветку от принятого integration HEAD — нативный скилл сам не коммитит.
- **Влитие**: оркестратор выполняет компактную проверку (`diff --stat`, состав изменений ↔ пункты блока, целевые проверки, формат коммита; полный смысловой разбор — только финальное ревью) и вливает одним squash-коммитом формата `Task: <change>#<номер>` + `refs #N` (номер — только из задачи исходной ветки; при отсутствии — вопрос пользователю); после проверки эквивалентности «squash ≡ tip блочной ветки» ветка удаляется — единственное точечное разрешение `git branch -D`.
- **Состояние**: компактный `run.json` (исходные ветка/HEAD, integration-ветка/путь/HEAD, стадия, последний принятый блок, блокер), один владелец, одна атомарная запись на переход; `tasks.md` — канонический список задач; состояния задач `pending / in-progress / accepted / blocked`; частичная работа при остановке легально остаётся в integration-worktree.
- **Тесты**: полный baseline не обязателен; сырой вывод сохраняется в temp-файл, ошибки извлекаются без повторных запусков; целевые проверки после каждого блока; полный прогон — один раз на итоговом HEAD; дублирование полных прогонов между ролями запрещено.
- **Гигиена контекста**: префлайт одним пакетом вызовов, артефакты читаются один раз, далее только указатели; поиск — по релевантным src/tests, исключая `bin`/`obj`/`.wf-research`/архивные спеки; делегированный код оркестратор глубоко не читает; отчёты компактны (HEAD, пункты, результат команд, блокер), состав файлов — из Git по необходимости.
- **Запреты**: `--no-verify` и отключение hooks; `git -D` вне случая проверенной блочной ветки; `refs #N` из артефактов change; разрушительные Git-операции без отдельного согласия.
- **Возврат**: неизменный — согласование с актуальной исходной веткой, отдельное согласие на перенос, `merge --ff-only`, отказ fast-forward — остановка с сохранением результата.

## Consequences

- Отказ от потенциального ускорения на действительно независимых крупных задачах; числовое ускорение не обещается — надёжной телеметрии времени и токенов в среде нет.
- Ошибки блока и частичная работа живут в integration-worktree, а не в отдельной worker-ветке; изоляции частичных результатов между задачами нет — блок принимается целиком до запуска следующего.
- Сокращение повторных проверок допустимо только при сохранении финальной приёмки (полный прогон на итоговом HEAD) и независимого итогового ревью по диффу «исходный HEAD → integration HEAD»; fix замечаний — отдельный суб-агент одним коммитом без `Task:`.
- Текущий текст `SKILL.md`/`execution.md` будет приведён к этой модели отдельным явным запросом пользователя; до этого действующий параллельный контракт остаётся в файлах скилла.
