# Стек — C#/.NET: один exe с Blazor Server и режимом --mcp, EF Core + SQLite

Журнал сделок — локальный персональный инструмент одного пользователя, поэтому решено строить его как единое приложение C#/.NET: веб-интерфейс Blazor Server, данные в SQLite через EF Core (режим WAL), а MCP-сервер — режим `--mcp` того же исполняемого файла (раннее ветвление до построения веб-хоста, stdio-транспорт, логи только в stderr). Исследования подтвердили практичность: официальный пакет `ModelContextProtocol` 2.2.0 вышел в GA и поддерживает stdio-сервер на `Host.CreateApplicationBuilder` ([#3](https://github.com/menshov-anatoliy/transaction-journal/issues/3)), REST API Bybit подписывается HMAC из чистого C# без сторонних SDK ([#2](https://github.com/menshov-anatoliy/transaction-journal/issues/2)). Решение принято при чартинге карты ([#1](https://github.com/menshov-anatoliy/transaction-journal/issues/1)).

## Considered Options

- Отдельный исполняемый файл для MCP-сервера — отклонён: два артефакта сборки и развёртывания вместо одного, дублирование конфигурации и доступа к базе.
- Node.js/TypeScript или Python SDK для MCP — отклонены: второй язык и рантайм ради одной функции к моменту решения не нужны, C# SDK уже GA.
- PostgreSQL или другой сервер БД — отклонён: персональный локальный журнал не оправдывает эксплуатацию отдельной СУБД; SQLite в WAL достаточен для одного пользователя и читающего MCP-напарника.

## Consequences

- Один exe обслуживает и веб-интерфейс, и MCP-клиентов; режим выбирается аргументом запуска.
- SQLite-файл — единственное хранилище; параллельные читатели MCP работают поверх WAL, не блокируя пишущее веб-приложение.
- Смена стека равнозначна переписыванию приложения — решение необратимо в пределах MVP и последующих итераций журнала.
