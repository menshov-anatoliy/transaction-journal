# Агентский цикл разработки

Как черновик идеи становится задачей, готовой для агента. Решение —
[ADR-0023](../adr/0023-sdlc-issue-and-adr-without-openspec.md), термины —
[GLOSSARY.md](./GLOSSARY.md), метки — [triage-labels.md](./triage-labels.md).

Цикл запускается локально вручную, без GitHub Actions. Спецификация живёт в
GitHub Issues, долговечные решения — в ADR, текущее поведение — в тестах с
traceability на `issue:#N` и `adr:`.

## Стадии

1. **Черновик идеи.** Человек создаёт issue по шаблону «Идея доработки» и
   получает метку `needs-triage`. Тело issue дальше не переписывается.
2. **Сессия опроса — `/triage #N`.** Синхронная агентская сессия: агент
   классифицирует issue (bug/enhancement), проверяет дубликаты и
   `.out-of-scope/`, выбирает трек и ведёт опрос (grilling + domain-modeling),
   по ходу обновляя ADR и глоссарий.
   - Если опрос не закончен, агент оставляет комментарий Triage Notes («что
     установлено / что осталось») и ставит `needs-info`. Это приглашение
     продолжить новой сессией `/triage #N`. Вопросов в комментариях
     асинхронно не задаём.
3. **Артефакт трека.**
   - **Срез** — одна задача, которая умещается в одно окно контекста:
     комментарий Agent Brief по `.agents/skills/triage/AGENT-BRIEF.md`.
     Контракт — бриф, тело issue — только контекст.
   - **Спека** — несколько срезов: `/to-spec` создаёт issue-спеку `#M`, а
     `/to-tickets #M` разбивает её на sub-issues с blocking-связями. Черновик
     закрывается комментарием «Superseded by #M».
   - **Карта** — работа на несколько сессий: `/wayfinder`
     (`wayfinder:map`), затем решения доводятся до трека «Спека».
4. **Ворота готовности.** Агент проходит чек-лист и спрашивает в сессии:
   «ставлю `ready-for-agent`?». Метку ставит только человек — ответ «да» и
   есть его подтверждение.
5. **Исполнение — `/implement #N`.** В отдельном worktree, результат — PR.
   Для среза можно поручить задачу Copilot cloud agent. После коммита агент
   оставляет в issue краткий отчёт об исполнении: коммит и ветка, что сделано
   по критериям приёмки, результат прогона тестов (с пометкой pre-existing
   падений, проверенных на чистой базе) и итог code-review.

## Чек-лист готовности

- [ ] Проблема и наблюдаемые критерии приёмки описаны.
- [ ] Назван тестовый шов, через который проверяется поведение.
- [ ] Явно указано, что не входит в охват.
- [ ] Указаны затронутые ADR и термины глоссария.
- [ ] Открытых вопросов нет.
- [ ] Blocking-связи с другими issue проставлены.
- [ ] Каждый срез умещается в одно окно контекста агента.

## Команды

| Шаг | Команда |
|---|---|
| Сессия опроса / её продолжение | `/triage #N` |
| Issue-спека из обсуждения | `/to-spec` |
| Разбиение спеки на срезы | `/to-tickets #M` |
| Карта крупной работы | `/wayfinder` |
| Реализация | `/implement #N` |

Тип issue различается по префиксу заголовка (`Идея:`, `Баг:`, `Спека:`,
`Срез k/n:`, `Карта:` …) — таблица в [issue-tracker.md](./issue-tracker.md#префиксы-заголовков).

Все комментарии, которые агент пишет при triage, начинаются с дисклеймера
`> *This was generated by AI during triage.*`.

## OpenSpec

Новые OpenSpec changes не создаются. Активные changes доводятся и
архивируются по прежнему процессу; `openspec/specs` и метки `openspec:`
заморожены как legacy.
