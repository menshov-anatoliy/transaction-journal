# Трассировка агентских вызовов и мониторинг в Arize Phoenix

Инструкция описывает, как в журнале транзакций устроена операционная трасса
агента (термин из GLOSSARY.md — инфраструктурный след одного агентского
вызова: фазы, вызовы модели и инструментов, метрики, ошибки и отмены), где
она хранится, как читается и как подключить Arize Phoenix для просмотра и
диагностики агентских вызовов.

Аудитория: разработчик или владелец, отлаживающий чат консультаций и проход
подсказок на своей машине.

Источники решений:

- [ADR-0020 — трассировка агентского харнеса](../adr/0020-agent-harness-tracing.md)
- Спецификация [ops/agent-tracing](../../openspec/changes/add-agent-tracing/specs/ops/agent-tracing/spec.md)
- Спецификация [config/tracing](../../openspec/changes/add-agent-tracing/specs/config/tracing/spec.md)
- Карта [#79](https://github.com/menshov-anatoliy/transaction-journal/issues/79)

## 1. Как устроена трассировка

Обе агентские поверхности — чат консультаций (`TransactionJournal.Chats`)
и проход подсказок (`TransactionJournal.Hints`) — трассируются единым
механизмом поверх OpenTelemetry-совместимых `ActivitySource`. Регистрация —
`AddAgentTracing` в `Program.cs` (composition root), слушаются три источника:

| Источник | Что пишет |
|---|---|
| `TransactionJournal.Chats` | корневой спан `chat_turn` на ход чата |
| `TransactionJournal.Hints` | корневой спан `hint_pass` и спаны фаз прохода |
| `Experimental.Microsoft.Extensions.AI` | встроенные спаны вызовов модели и тулов |

Ключевые свойства механизма:

- **Всегда включена, без сэмплирования** (семплер `AlwaysOn`). Трасса,
  которой нет в момент инцидента, бесполезна, а однопользовательский
  локальный трафик даёт мизерный объём.
- **Артефакт истины — локальный JSONL-файл**, а не внешний сервис. Phoenix —
  только dev-опция просмотра, прод и файл от него не зависят.
- **Захват metadata-only**: полные тексты prompt/completion не пишутся никогда
  (`EnableSensitiveData` всегда `false`); записываются метрики, статусы,
  метаданные и компактные аргументы тулов.
- **Запись фоновая** (`BatchActivityExportProcessor`): стриминг ответа чата
  не блокируется диском; сбой записи деградирует в диагностику и не ломает
  работу агента.

## 2. Модель спанов

### 2.1. Ход чата консультаций

Водопад одного хода (от вопроса владельца до конца стрима ответа):

| Спан | Источник | Что несёт |
|---|---|---|
| `chat_turn` | `TransactionJournal.Chats` | корень хода: `tj.chat.iterations` (число запросов модели), `tj.chat.id`, `tj.chat.message.id`, `tj.chat.cancelled=true` при отмене (статус остаётся не-ошибкой) |
| `chat {model}` | M.E.AI | один запрос к модели: метрики `gen_ai.*` — модель (`gen_ai.request.model`), токены, задержка |
| `orchestrate_tools` | M.E.AI | агентный цикл выбора инструментов |
| `execute_tool {name}` | M.E.AI | вызов одного тула: длительность, `gen_ai.tool.name`, `error.type` при сбое; на уровне `detailed` — событие `tj.tool.args` (JSON аргументов, обрезанный до 2 КБ с маркером усечения) |

Встроенные спаны Microsoft.Extensions.AI используются как есть, собственных
дубликатов нет. Отдельных событий итераций тоже нет — задержки итераций
читаются из длительностей встроенных `chat {model}`.

### 2.2. Проход подсказок

Проход детерминирован и модель не вызывает — на его спанах нет атрибутов
`gen_ai.*`. Корень `hint_pass` несёт исход (`tj.hints.outcome`:
`completed`, `skipped-market-unavailable`, `corpus-invalid`) и счётчики
(`tj.hints.created`, `tj.hints.expired`). Дочерние спаны фаз:

- `hint_pass.corpus_snapshot` — снимок корпуса правил;
- `hint_pass.expire_withdrawn_rules` — гашение выведенных правил;
- `hint_pass.journal_snapshot` — снимок журнала;
- `hint_pass.expire_closed_subjects` — гашение закрытых субъектов;
- `hint_pass.quotes` — рыночные котировки (сетевая задержка источника видна
  отдельным спаном);
- `hint_pass.evaluate_triggers` — оценка триггеров.

Собственные атрибуты системы используют только префикс `tj.*`; имена
semconv `gen_ai.*` не переименоваются — на них опирается LLM-семантика
Phoenix.

## 3. Локальный журнал трасс (артефакт истины)

Спаны пишутся в `App_Data/traces/traces.jsonl` относительно корня содержимого
приложения. Формат — плоский JSONL, одна строка = один спан, строка
самодостаточна для grep:

```json
{"ts":"...","service":"transaction-journal","source":"...","name":"chat_turn",
 "kind":"Internal","trace_id":"...","span_id":"...","parent_span_id":null,
 "duration_ms":8123.4,"status":"ok","status_desc":null,"attrs":{...},
 "events":[{"ts":"...","name":"tj.tool.args","attrs":{...}}]}
```

Ротация: при превышении `MaxFileBytes` (дефолт 10 МБ) текущий файл
переименовывается в `traces-{timestamp}.jsonl`, запись продолжается в новый
`traces.jsonl`; хранится не более `KeepFiles` архивов (дефолт 5).

### Grep-рецепты (PowerShell)

Найти трассу по trace id (включая архивы):

```powershell
Select-String -Path .\App_Data\traces\traces*.jsonl -SimpleMatch '<trace_id>'
```

Ошибки в трассах:

```powershell
Select-String -Path .\App_Data\traces\traces*.jsonl -SimpleMatch '"status":"error"'
```

Отменённые владельцем ходы чата:

```powershell
Select-String -Path .\App_Data\traces\traces*.jsonl -SimpleMatch '"tj.chat.cancelled":true'
```

Вызовы тулов:

```powershell
Select-String -Path .\App_Data\traces\traces*.jsonl -SimpleMatch 'execute_tool'
```

## 4. Корреляция трасс с доменными записями

Корреляционный ключ — W3C TraceId корневого спана (`chat_turn` /
`hint_pass`), 32 hex-символа; это же значение — поле `trace_id` в JSONL и
идентификатор трейса во вьюере.

| Направление | Как работает |
|---|---|
| Запись → трасса | ответ помощника несёт `messages.trace_id`; созданные подсказки — `hints.trace_id` (все записи прохода — один id; гашение в `expired` id не получает) |
| API → трасса | `GET .../chats/{chatId}/messages` возвращает trace id сообщения; `POST /api/hints/pass` — trace id прохода (поля опциональные, null у записей до внедрения) |
| Трасса → чат | атрибуты `tj.chat.id` / `tj.chat.message.id` на `chat_turn` покрывают и отменённые ходы, у которых записи-носителя нет |

Колонки trace id — метаданные отладки: ни одно доменное правило их не
читает.

## 5. Конфигурация (секция `Tracing`)

Параметры журнала трасс задаются конфигурацией, без правки кода. Опции
читаются один раз при старте приложения — после правки нужен перезапуск.

| Ключ | Значение | Дефолт |
|---|---|---|
| `Tracing:Detail` | уровень детализации: `basic` (имена, длительности, статусы, `gen_ai.*`, корневые спаны) или `detailed` (плюс события `tj.tool.args`) | `detailed` |
| `Tracing:Dir` | каталог трасс (относительный — от корня содержимого) | `App_Data/traces` |
| `Tracing:MaxFileBytes` | предел размера файла до ротации, байты | `10_485_760` (10 МБ) |
| `Tracing:KeepFiles` | число хранимых архивов | `5` |
| `Tracing:OtlpEndpoint` | приёмник OTLP для dev-просмотра в Phoenix; пусто/отсутствует — экспорт выключен | не задан |

Отсутствие всей секции даёт дефолты. Нечисловые или неположительные лимиты
откатываются к дефолтам; неизвестное значение `Detail` — ошибка запуска с
перечнем допустимых (молчаливая подмена уровня скрыла бы потерю событий
аргументов тулов).

Пример `appsettings.Local.json`:

```json
{
  "Tracing": {
    "Detail": "detailed",
    "OtlpEndpoint": "http://localhost:4317"
  }
}
```

То же переменными окружения:

```powershell
$env:Tracing__Detail = 'detailed'
$env:Tracing__OtlpEndpoint = 'http://localhost:4317'
```

## 6. Просмотр трасс в Arize Phoenix

Phoenix — рекомендованная dev-опция просмотра: единственный
одно-контейнерный приёмник OTLP с LLM-семантикой (модель, токены, вызовы
тулов) из `gen_ai.*` на приёме. Запасная «нулевая» альтернатива — .NET
Aspire Dashboard (MIT, без LLM-семантики).

### 6.1. Запуск Phoenix

```powershell
docker run -d --name phoenix -p 6006:6006 -p 4317:4317 arizephoenix/phoenix
```

- UI: <http://localhost:6006> (проект по умолчанию — `default`);
- приём OTLP gRPC: `localhost:4317`;
- без подмонтированного тома данные живут до перезапуска контейнера — для
  dev-просмотра этого достаточно, артефакт истины остаётся в JSONL.

### 6.2. Включение экспорта

1. Задайте `Tracing:OtlpEndpoint = http://localhost:4317` (см. раздел 5) —
   ключ обязан содержать схему `http://`.
2. Перезапустите приложение: OTLP-экспортёр подключается при старте.
3. Сделайте ход чата или запустите проход подсказок и откройте в Phoenix
   проект — трейсы появляются в течение секунд (батч-экспорт).

Без ключа трассы живут только в локальном JSONL, внешних зависимостей нет.
Чтобы выключить экспорт — уберите ключ (или оставьте пустым) и перезапустите
приложение.

### 6.3. Чтение трейсов

- **Водопад** трейса показывает всю иерархию: `chat_turn` → `chat {model}` /
  `orchestrate_tools` / `execute_tool {name}` или `hint_pass` → фазы.
- **Поиск по trace id**: возьмите trace id из записи чата/подсказки или
  ответа API и вставьте в поиск Phoenix — откроется именно эта трасса.
- **LLM-семантика**: спаны модели автоматически размечены из `gen_ai.*` —
  модель, токены, длительность; вызовы тулов видны как вложенные спаны.
- **Статусы**: ошибки спана выделяются статусом; отменённый ход ошибкой не
  является — ищите его по `tj.chat.cancelled`.

Ограничения: лицензия Phoenix ELv2 — только внутреннее dev-использование;
полных текстов prompt/completion в Phoenix нет (их нет нигде — захват
metadata-only); агрегированных сводок по дням/моделям/тулам система не
ведёт — метрики per-trace.

## 7. Мониторинг: типовые сценарии диагностики

| Симптом | Где смотреть | Что проверить |
|---|---|---|
| Медленный ответ чата | водопад `chat_turn` | сколько `chat {model}` в ходе (`tj.chat.iterations`); какая итерация тянет длительность; не упёрлись ли в потолок 6 итераций (`MaximumIterationsPerRequest`) |
| Тул падает или тормозит | `execute_tool {name}` | статус/error.type сбойного тула; на `detailed` — `tj.tool.args` (что именно передали); систематичность по нескольким трейсам |
| Большой расход токенов | `chat {model}`, метрики `gen_ai.usage.*` | какие ходы и итерации потребляют токены; влияние числа итераций |
| Ход оборвался | `chat_turn` с `tj.chat.cancelled=true` | это отмена владельцем (не ошибка); сколько итераций успело выполниться |
| Проход подсказок ничего не создал | `hint_pass` | исход `tj.hints.outcome` (`skipped-market-unavailable` — рынок недоступен, `corpus-invalid` — корпус невалиден); задержка `hint_pass.quotes`; счётчики `tj.hints.created` / `tj.hints.expired` |

## 8. Корректировка

### 8.1. Настройки трассировки — конфигурацией

Уровень детализации, каталог, лимиты ротации и приёмник OTLP меняются
правкой секции `Tracing` без правки кода (раздел 5). Типовые случаи:

- уменьшить объём — `Tracing:Detail=basic` (уйдут события `tj.tool.args`);
- перенести журнал — `Tracing:Dir` в абсолютный путь;
- держать больше истории — `Tracing:MaxFileBytes` / `Tracing:KeepFiles`;
- отключить внешний экспорт — очистить `Tracing:OtlpEndpoint`.

### 8.2. Поведение агента — по выводам мониторинга

Трассировка поведение не меняет, но указывает, что править. Найденное в
Phoenix или JSONL фиксируйте правкой кода харнеса через обычный процесс
(OpenSpec change с traceability-разметкой). Типовые выводы:

- `tj.chat.iterations` стабильно близко к потолку 6 → агент циклится:
  пересмотреть промпт/набор тулов или потолок в `ChatAgent`;
- один тул стабильно в ошибках (`error.type`) → чинить сам тул, трасса
  указывает аргументы (`tj.tool.args`) и место в ходе;
- задержка ходов определяется моделью, а не тулами → рабочая модель чата в
  секции `Llm` (см. `appsettings.Local.json.example`);
- `hint_pass.quotes` — доминирующая фаза по времени → смотреть источник
  котировок, а не код оценки триггеров.

## 9. Чек-лист проверки работоспособности

1. После хода чата файл `App_Data\traces\traces.jsonl` растёт, строки —
   валидный JSON с `"service":"transaction-journal"`.
2. Trace id из ответа API (`GET .../chats/{chatId}/messages`,
   `POST /api/hints/pass`) находится в файле grep'ом по этому id.
3. При включённом `Tracing:OtlpEndpoint` и запущенном контейнере трейсы
   появляются в UI Phoenix (<http://localhost:6006>) с LLM-семантикой.
4. Остановка контейнера Phoenix не влияет на работу приложения — трассы
   продолжают писаться в JSONL.
