# openspec-apply-all

Оркестратор последовательного исполнения одного OpenSpec change. Вся работа идёт в едином integration-worktree с собственной integration-веткой; исходная ветка и рабочий каталог остаются пользователю. Реализацию делает по одному **синхронному блочному исполнителю** — суб-агенту, который вызывает скилл `openspec-apply-change` с жёстким охватом пунктов блока и коммитит во временную блочную ветку. Оркестратор владеет планом, состоянием и влитием; его контекст не засоряется кодом. В конце предложи слияние — выполняется только после отдельного согласия. Пуш, PR и архивация — вне этого скилла.

**Блок** — по умолчанию один пункт `tasks.md`. Укрупнение — только явной группировкой пользователя:

> Выполни блоками: 1.1, 1.2 — первый блок; 1.3, 2.1 — второй.

либо одним вопросом оркестратора на планировании, если пункт потребляет контракт или результат соседнего; решение всегда за пользователем. Неупомянутые пункты остаются отдельными блоками. Частичный прогон задаётся явно: «выполни только 1.1 и 1.2».

## 1. Префлайт и план

1. Определи change по аргументу или контексту; иначе используй `openspec list --json`. При нескольких подходящих change задай один вопрос о выборе. Все CLI-команды выполняй в явно выбранном каталоге; при выбранном OpenSpec store сохраняй его scope. Префлайт делай одним пакетом вызовов.
2. Прочитай `openspec status --change "<change>" --json` и `openspec instructions apply --change "<change>" --json`. Загрузи **все** `contextFiles`, обязательный `context` и применимое `operationGuidance`; соблюдай `planningHome`, `changeRoot` и `actionContext`. Состояние `blocked` останавливает реализацию. CLI — источник статуса, состава задач и расположения их отметок. Сокращай представление CLI без потери этих данных; артефакты читай один раз, дальше передавай указатели на них в нужном worktree.
3. Зафиксируй исходный каталог, ветку и HEAD. Detached HEAD требует выбора исходной ветки. Незакоммиченный код не препятствует запуску и остаётся в исходном каталоге. Если артефакты выбранного change не закоммичены, отличаются от HEAD или недоступны в изолированной базе, остановись и предложи зафиксировать их; ничего автоматически не коммить и не копируй.
4. Перед созданием worktree прочитай [execution.md](execution.md): роли, изоляция, состояние и возобновление. Для выбора прежнего прогона сначала читай только поля состояния, нужные для выбора и восстановления; детали — при расхождении. При существующем незавершённом прогоне того же change продолжай его integration-ветку и план; несколько прогонов требуют выбора пользователя. При `all_done` нового прогона сообщи об отсутствии работы; для существующего проверь, не осталось ли финальной приёмки или переноса результата.
5. Нормализуй группировку и охват по правилам [execution.md](execution.md). Построй линейную последовательность блоков по явным зависимостям, потребляемым контрактам и общим изменяемым областям; соседство в списке само по себе порядок не задаёт. Неясная зависимость — вопрос до запуска затронутого блока.
6. Покажи компактный план: исходная база, integration-ветка/worktree, охват, «блок → пункты → зависимости», формат влития. Сохрани состояние. Если вопросы решены, начинай без дополнительного подтверждения: запуск скилла разрешает изолированную реализацию, но не слияние в исходную ветку.

## 2. Исполнение блока

Одновременно активен ровно один блочный исполнитель; следующий блок начинается только после влития предыдущего.

1. Подготовь integration-worktree: чистое состояние, integration-ветка, принятый HEAD. Создай от него блочную ветку по правилам [execution.md](execution.md).
2. Запусти **синхронного** суб-агента `general-purpose`. Передай:
   - абсолютный путь integration-worktree, блочную ветку и базовый HEAD;
   - требование вызвать скилл `openspec-apply-change` с охватом «только пункты блока» — нативный скилл иначе обойдёт все незавершённые пункты;
   - пункты блока, границы изменяемого кода и критерии приёмки;
   - артефакты change и проектные инструкции **в его worktree**, включая `AGENTS.md`, правила оформления, тестов и traceability;
   - правила компактной передачи из [execution.md](execution.md): в ответе HEAD блочной ветки, пункты, выполненные проверки и результаты, блокер; подробности — в каталоге прогона.
3. Исполнитель работает в integration-worktree на блочной ветке: реализует только пункты блока; отметки `- [ ]` → `- [x]` в `tasks.md` делает сам; паузы нативного скилла («спроси пользователя») транслирует в блокер оркестратору. Коммитит реализацию с отметками в блочную ветку; `run.json` общего прогона принадлежит только оркестратору. «Готово» — полностью выполненный блок, а не частичный результат.
4. Если суб-агенты недоступны, сообщи ограничение и предложи пользователю выбор: оркестратор выполняет блоки сам по тем же правилам или прогон останавливается.

При провале исполнителя или влития переходи к разделу «Остановка и возобновление» в [execution.md](execution.md): новые блоки не запускаются, автоматических повторов нет.

## 3. Влитие блока

1. Компактная проверка блочной ветки: `diff --stat`, состав изменений соответствует пунктам блока, целевые проверки выполнены исполнителем, формат коммита корректен. Полный смысловой разбор — только финальное ревью.
2. Переключи integration-worktree на integration-ветку и влей блочную ветку одним squash-коммитом. Подготовь сообщение без BOM по правилам [execution.md](execution.md); перед каждым зависимым действием проверь код завершения команды. Проверь эквивалентность деревьев «squash ≡ tip блочной ветки»; после этого удали блочную ветку — единственное разрешённое `git branch -D`.
3. Подтверди через CLI, что пункты блока отмечены, а остальные отметки сохранены. Одной атомарной записью согласованно обнови стадию, принятый HEAD, охват и решение о переносе по правилам [execution.md](execution.md). Только теперь начинай следующий блок.

Формат squash-коммита:

- subject — Conventional Commits по сути изменения;
- body — отдельная строка `Task: <change>#<номер>` для каждого пункта блока и краткое описание приёмки;
- `refs #N` — номер задачи из имени исходной ветки по правилам репозитория; не из артефактов change и не из технических имён веток; при отсутствии — один вопрос пользователю;
- `Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>`.

## 4. Финальная приёмка и возврат

1. После влития всех выбранных блоков выполни полный применимый набор существующих тестов и сборок **один раз** на итоговом HEAD; обязательные проверки change остаются частью приёмки. Сырой вывод сохраняй в temp-файл и извлекай ошибки без повторных запусков. При частичном охвате сообщай «выбранные задачи завершены», а не «change завершён».
2. Запусти суб-агента, вызывающего скилл `code-review`, по всему диффу от **исходного HEAD до integration HEAD**. Передай путь integration-worktree и точные границы ревью.
3. Подтверждённые замечания устраняет один синхронный fix-исполнитель в том же integration-worktree на integration-ветке одним коммитом соответствующего типа, без `Task:`; повтори затронутые проверки и убедись, что замечания устранены. Провал останавливает прогон.
4. Согласуй результат с актуальной исходной веткой и предложи слияние по разделу «Возврат результата» в [execution.md](execution.md). Отказ, отсрочка или недоступность безопасного слияния сохраняют готовый результат в integration-ветке/worktree.
5. Выполни очистку по [execution.md](execution.md). Отчёт: change и охват, завершённые/оставшиеся пункты, исходная база, integration-ветка/HEAD и путь, принятые коммиты, итоги приёмки/ревью, статус слияния либо причина остановки.

Минимум шума: план, `▶ <блок или пункт>`, `✔ <пункты> → <hash>`, блокер и финальный отчёт. Подробности сохраняются в состоянии прогона и отчётах исполнителей вне исходного рабочего каталога.
